# ORTG v2 策略规则表

与 `logic.go` 不一致时以代码为准。

## 状态判定（每次对账，逐文件，按顺序取第一个命中）

| 顺序 | 状态 | 条件 | 对账动作 | 报告 |
| --- | --- | --- | --- | --- |
| 1 | 忽略 | 命中内置排除或 JSON 忽略规则 | 既有行直接删除，不进表不渲染 | 计数并计入已清除 |
| 2 | 计划新建 | 磁盘无文件，行从未记录过指纹，有目标纲要 | 不置墓碑 | 列出 |
| 3 | 已删除待确认 | 磁盘无文件，其余情况 | 置 deleted=1 作墓碑；文件回到磁盘即清墓碑 | 列出；deleted 与 target_delete 同为 1 的行由 Purge 清除，本轮清除的不再列出 |
| 4 | 无纲要 | 新文件，或 outline 为空 | 插骨架行并记录指纹 | 列出（纲要里只显示裸文件名） |
| 5 | 过期 | 指纹变化且纲要写入时间不晚于文件修改时间（秒级，同一秒算过期） | 无（等模型更新） | 列出 |
| 6 | 待执行 | 有目标纲要或目标删除 | 无 | 列出 |
| 7 | 对齐 | 其余；指纹变化但纲要更新时静默前移指纹 | Align | 只计数 |

内置排除：`.git/`、`build/`、`ortg.tsv`、`ortg.tsv.*`、`overview*.txt`，超过 4 MB 的文件按忽略处理。

目标纲要是什么：这个文件改完之后应有的纲要，用来指导接下来改代码——代码改到符合它、用 `ortg_update` 提交后自动清空。待核查、待实测的结论和疑问不是目标，不写进目标纲要，也不写进当前纲要：先核查，再把事实写进当前纲要。它原名"未来纲要"（标记 `#未来:`、工具 `ortg_future`），因为"未来"只说"以后"、被当成了待办事项的去处，改名为目标纲要（`#目标:`、`ortg_target`）；旧标记 `#未来:` 由 `migrate.Document` 在导入 overview.txt 时换掉；`ortg_target` 的 document 只认 `#目标:`。`ortg.tsv` 的列名随之改为 `target_outline`、`target_time`、`target_delete`（模型会去读这个文件），Go 代码里的 Future 名字也都改成了 Target。改名前写的表（列名 `future_*`、纲要头里写着"未来规则""未来纲要""#未来:""ortg_future"）由 `migrate.Table` 就地升级，见下文"旧格式迁移"。

依赖稀疏处切、公共底层单独成模块、目录纲要随用到它的模块、每模块宜在单次上限的十分之一以内），要模型拟方案给用户、同意后再改 B 标签并登记 #B 字典，并且不计为已发。纲要只走 MCP、不走 hook：Claude Code 对 MCP 结果默认超过 50000 字就存成文件只给 2KB 预览，所以 ortg_overview 在工具定义的 _meta 里声明 model_context_window 把上下文调到模型允许的最大值），MCP 进程还要设 env `ORTG_AGENT=codex` 才按 Codex 计大小。大小一律按宿主自己的算法计（`outlineSize`）：Claude Code 按 JS 字符串长度（UTF-16 码元，基本平面外的字符算 2），Codex 按 ⌈UTF-8 字节 ÷ 4⌉ 估 token；而两个宿主对 hook 注入都写死约 1 万（Claude 1 万字、Codex 约 1 万字节）且不可调。每种回复最后一行都以"以上"开头（条目 overviewPartFooter、目录、短回复各一句）；Codex 截断时留首尾、中间换成 `…N tokens truncated…`，所以判断截断要两条一起看：最后一行不是"以上"开头，或正文出现 `tokens truncated` |
| ortg_status | 无 | 重新扫描并对账，只返回对账报告，不返回纲要正文。被问纲要状态时用它，开工报告只是快照 |
| ortg_update | path, outline（path 可为绝对路径） | 磁盘不存在或命中排除/忽略规则则拒绝；校验格式与字典；写 outline，前移指纹；清空目标纲要；返回状态与警告。这次纲要的依赖（Uses，`-` 算没有依赖）与原纲要不同时，回复附一句提醒（纲要头还是模板时不提醒；文件第一次提交纲要时，只在表里已没有别的文件缺纲要时提醒——还有别的文件缺纲要说明正在批量建纲要，逐个提醒只是刷屏）：看纲要头里描述依赖与分层的部分（如【依赖层次】）是否随之不准，不准就用 ortg_header 改——纲要头不会自动跟着 Uses 变 |
| ortg_target | path + outline，或 path + delete=true，或 items，或 document | 写目标字段；items 一次写多个文件，每项 `路径 目标纲要行`（`=` 表示纲要不变，`删除` 表示计划删除），逐项报告，失败项不影响其余，全部失败才报错，给了 items 就不看 path/outline/delete；document 整份导入，**条目一律进目标纲要列**，纲要头进表头（渲染时加的 #代码纲要 标记行先剥掉）。不按文件是否存在分流——那是建表的语义，这里是提交计划，绝不能覆盖已有纲要。outline 传 `=` 表示只改实现、改完纲要不变（重构、格式化、修 lint）：程序把现在的纲要写进目标纲要，模型不用把整行再抄一遍；文件还没有纲要时拒绝。目标与现在的纲要相同时，渲染只出一行 `#目标:同现在(只改实现,改完纲要不变)`，`ortg_review` 也只列一句——理由：一次全仓库风格整理曾让 46 个文件的目标纲要原样抄写现在的纲要，整份发送因此多出 5.4 万字 |
| ortg_review | rulings（可选，字符串数组，每条 `契约键：裁决`） | 核对改动计划：列出每个有目标纲要的文件（要改、新建、删除）的现在→目标字段变化、格式不合格的目标行、Uses 依赖它们却还没有目标纲要的文件、计划外同概念的「必须保持」条目（`relatedContracts`：取各计划文件目标纲要里新出现、现在纲要里没有的标识符（≥6 字符，出现在超过十分之一纲要里的不算），在计划外的纲要 Constraints 与纲要头里找含「必须保持」且同名的子句——相等，或较短者≥9 字符且被较长者包含——按共享标识符个数、再按稀有度排序列原文，至多 15 条，要求逐条说明新实现是否仍满足。理由：把一个限额从输出层移进底层的计划里，守护这条行为的契约写在输出层的纲要里，计划文件与它没有 Uses 关系，核对从没列出它，改坏了守护测试），再给逐项核对清单（接口与调用方、数据与约定、纲要头约定、新建与删除、测试与文档、目标纲要本身、守护测试、测试入口、执行点、收尾整包验证）。同一计划的后续核对只回差量（`planSeen`，随 sentCache 存盘）：目标纲要与上次所示相同的文件只列一句 `reviewUnchanged`，已给过正文的契约只列 `reviewKeySeen`（仍算给了正文，照样要裁决），上次列过的依赖方与同名兜底条目只给个数，`reviewConflict` 与核对清单每计划各发一次；计划文件与上次核对没有交集即视为新计划，收敛后也从头再来。理由：本仓库自己一次 8 个文件的计划，第二次核对逐字重复了约 1.5 万字。每次调用记下它看到的计划；连续两次看到的计划一样、且给了正文的绑定契约（见下文跨模块契约）在 rulings 里都有裁决即收敛（缺的列在 `reviewRulingsMissing` 里，不收敛），收敛时把每条裁决写进该契约登记行末尾的 `；【裁决】…`（替换旧的），计划里的文件在本上下文解锁可写（之后 ortg_update 清掉目标纲要也仍可写），压缩/清空后要重新核对。只给模型自查，不等用户 |
| ortg_align | mode=all 或 mode=paths + paths | 前移指纹与纲要时间，不改文本 |
| ortg_header | header, ignore_dirs, ignore_files, keep_files, observe_dirs, observe_files, dirs(目录=标题) | 整块替换纲要头（须含 #A/#B/#E 字典）与配置；只覆盖传了的字段，没传的原样保留，传了的列表整体替换。dirs 只是纲要里目录段的标题 |

无表时 ortg_overview 与 `ortg scan` 建表：根目录有 overview.txt 则整份导入为目标纲要，否则用模板建空表；随后把 `ortg.tsv.*` 写入 `.git/info/exclude`。

**首次建纲要：文档 → 纲要头 → 源码**：纲要头里还留着模板【部署】或【系统】的占位行时，视为纲要头没写，进入首次建纲要。此时 `ortg_update` 只收文档文件（`isDocFile`：`.md`、`.rst`、`.adoc`、`.txt`，或路径里含 `docs/`、`doc/`、`guide/`、`guides/` 段，规则对所有仓库一样）的纲要，源码纲要与 `ortg_target`（单个文件、计划删除）一律拒绝；`ortg_header` 要把纲要头写成正式内容时，非观察档的文档必须都已有纲要，否则拒绝并列出缺的文档（只改忽略、观察等配置不拦，同一次调用里先把文档放进观察档也算）；`document` 整份导入自带纲要头，允许，但导入后仍是模板也拒绝并回滚。`ortg_overview` 回复开头按进度给指引：还有文档没纲要时列出它们（README 在前，至多 20 个，超出写「等 N 个」），要求逐份读全文写文档纲要；文档纲要齐了要求据此与目录结构写纲要头；仓库没有文档时要求读入口文件与目录结构写纲要头。文档文件的 Constraints 按 1200 字配额（`docQuota`），不按重要度：它写文档规定的约定、约束与设计决定，是写纲要头与源码纲要的依据。纲要头写好后不再有文档门禁，已建好纲要的仓库不受影响。**收尾提炼**：纲要头写好后，补上表里最后一个缺纲要的文件（首次提交、提交后没有别的非观察档文件缺纲要）且还有文档在认知档时，`ortg_update` 回复附一句收尾提示（`distillNote`，列出这些文档）：把文档放进观察档（`observe_files`/`observe_dirs`），纲要里不再重复；放之前逐份逐条核对文档纲要 Constraints 里每条约定、约束与设计决定现在写在纲要头哪一段或哪个源码纲要里，找不到落点的先补上（纲要头用 `ortg_header`，源码纲要用 `ortg_update`），文档与代码的不一致也落到对应源码纲要——文档进了观察档，它的纲要就不再发给模型，没落下的内容会丢。程序判断不了覆盖与否，只能靠这句要求；文档以后改了，对账报「观察变动」时重读它、同步纲要头与源码纲要再 `ortg_align`。要留在纲要里的文档（如顶层 README）可以不放。测试同理：观察档里的测试（含整个测试目录）只记指纹、不发给模型，收尾时逐个确认它们锁定的对外行为已按测试契约写进被测源码纲要或纲要头。建源码纲要时就要一并读它的单元测试与相关集成测试（建表指引写明）。这只是提示，程序不强制；重写已有纲要不触发。文档只作背景，与代码不一致时按代码写，并在那份文档的纲要 Constraints 里记下不一致之处。理由：纲要头是全局认知，文档纲要是它的依据；程序判断不了模型读没读文档，但能判断文档有没有纲要。

扫描枚举以 git 为准并逐仓库进行：根仓库跑一次 `git ls-files`，再用文件系统遍历找出嵌套的子仓库（发现后继续下钻，多层也能浮出来）各自跑一次，路径加前缀后合并去重。发现子仓库不能问父仓库的 git——git 从不下钻嵌套工作树，根仓库的忽略规则也不管辖它的子仓库（根 `.gitignore` 常有 `/*/` 把所有一级目录藏起来，正是这条遍历要治的盲区）。但**嵌套**仓库的忽略规则算数：一个仓库若落在上层仓库忽略的目录里（vendor/、node_modules/ 之类），连同子树一起跳过——那个项目已经声明了那不是自己的代码。只有目录规则参与剪枝；文件级 pattern 不剪，否则"新被忽略的文件要掉行"依赖的先列出再判 ignored 再 Purge 链路会断。

文件分三档角色，判定顺序 内置结构性排除 > `keep_files` > `observe_dirs`/`observe_files` > `ignore_dirs`/`ignore_files`：**认知**档要写纲要；**观察**档记指纹、报变动但从不要求纲要，也不渲染进整份纲要（`ortg_update` 对它直接拒绝，并指出走 `keep_files`）；**排除**档完全不看。观察档指纹变了报"观察变动"，`ortg_align` 前移指纹即确认——它不是门禁，不阻断任何操作。对账报告里观察档只计数（`观察 N`），只有变动的列出路径。hook 对观察档一律静默。

`ignore_dirs`/`ignore_files` 之外还有 `keep_files`：命中它的路径不再被 JSON 忽略规则排除（压不过调用方内置的结构性排除，ortg.tsv、overview*.txt、build/ 永远在表外）。带 keep 的目录即使命中忽略也照样参与遍历与枚举——先剪掉就再也捞不回来了（取反项不算"这里有白名单目标"，不会让被忽略的目录重新参与遍历）。

**每份名单内部照抄 gitignore**：从左到右扫、后匹配者胜、`!` 前缀取反；同一档内先扫目录名单再扫文件名单，于是具体的文件规则能在宽的目录规则上挖洞（`ignore_dirs: ["vendor"]` + `ignore_files: ["!vendor/keep.go"]`）。整棵留下再挖洞不必拆成几十条：`keep_files: ["composetp/**", "!composetp/vendor/**", "composetp/vendor/critical.yml"]`——留整棵、挖掉 vendor、洞里再把 critical.yml 打回来。**档与档之间的优先级固定，不受名单内顺序影响。**

表里有行、枚举不到、磁盘上却还在的路径：带纲要或目标纲要的按存在处理（被 .gitignore 点名的文件仍有认知，不能当墓碑），只有裸文件名的骨架行判为忽略并由 Purge 清掉——它已经移出扫描范围，留着只是噪音。

建表前先把 overview.txt 重命名为 overview.txt.bak（已存在则 .bak.2、.bak.3，绝不覆盖已有备份）：内容已读进内存，挪开是免得这份旧纲要留在原处，被模型 cat/grep 当成纲要读而绕过 ortg_overview；导入失败时迁移步骤要读的正是这份备份，迁移提示会报出备份名。表不导出任何文本文件——纲要只在 ortg.tsv，只经 ortg_overview 发给模型。建表前已有的 ortg.tsv.bak 原样保留（用户可能正要拿它恢复丢失的表），没有则不留下导入时生成的模板备份；建表后在后台拉起 CBM 建图（`ortg graph`），会话中途建的表也有改动前的调用图可查。

为什么只有 gate 用 `mcp_tool`：command 钩子每次起一个新的 `ortg hook` 进程，看不到 MCP 进程内存里"本会话已发过哪些纲要"；`mcp_tool` 钩子由宿主直接调本会话已连上的 ortg MCP 进程，状态就在它内存里，不需要会话 id、文件或进程识别。其余钩子不改：SessionStart、SubagentStart、PostCompact 属于 Claude 不等待 MCP 连上的事件，启动时 ortg MCP 常常还在连接，改成 `mcp_tool` 会被跳过、规则块与对账报告丢失；post 钩子要跑 2–18 秒 CBM，放进 MCP 会堵住它单线程的请求循环；command 钩子也不依赖 MCP 进程活着。Codex 用单独的 `hooks/codex.json`（`.codex-plugin/plugin.json` 指向它）：command 钩子与 `hooks/hooks.json` 一模一样（`manifest_test` 盯着），gate 单独写一条——Codex 的 MCP 服务器名是 `config.toml` 的键（`ortg`），不是插件名 `plugin:ortg:ortg`；matcher 只有 `Bash|apply_patch|ApplyPatch`（Codex 没有 Read/Grep 工具）；`input` 只用 `${tool_name}` 与 `${tool_input.command}`，因为 Codex 遇到调用里没有的字段会让整条钩子失败。Codex 0.156 起支持 `mcp_tool` 钩子（除 SessionEnd 外的事件），PreToolUse 同样认 `permissionDecision: deny` 与 `additionalContext`。实测 Codex 0.157.1：模型的 shell 调用包在 JS `exec` 工具里（`tools.exec_command`），PreToolUse 仍以 `tool_name=Bash`、`tool_input.command` 触发，被拒时界面显示 "Blocked by hook" 并把理由交给模型；Codex 比 Claude 更守"开工先取纲要"，gate 主要在上下文重置后起作用。

Codex 的 `apply_patch`：载荷 `tool_name` 为 `apply_patch`，`tool_input.command` 是整段补丁（实测 codex-cli 0.154）。hookio 只从行首的 `*** Update File:` / `*** Add File:` / `*** Delete File:` 取路径（补丁正文里的同样字样不算），与 file_path 合并去重成 FilePaths；logic 对其中每个落在仓库内的文件分别应答再拼接，越界路径丢弃。只有工具名是 apply_patch 才解析补丁，Bash 命令里出现补丁字样不算。

宿主判定：`ORTG_AGENT` 优先；否则有 `PLUGIN_ROOT` 或 `PLUGIN_DATA` 即 codex。实测 Codex 给 hook 同时导出 `PLUGIN_*` 与兼容用的 `CLAUDE_PLUGIN_*`，Claude Code 只给 `CLAUDE_PLUGIN_*`——所以不能以 `CLAUDE_PLUGIN_ROOT` 为空判 codex，那样会把 Codex 认成 Claude、漏掉下面的预算补充。

宿主差异只有一处：`base.Host()` 判为 codex 时，规则块尾部多一句 Codex 宿主补充——该宿主用 `functions.exec` 包装 MCP 调用，工具结果超过预算会被从中间截掉、只留首尾（不报错），故要求调用 `ortg_overview` 时外层命令第一行写 `// @exec: {"max_output_tokens": 500000}`（与 `codexLimits.max` 一致），并以"最后一行是以'以上'开头的收尾句、且正文没有 `tokens truncated`"作为完整到达的判据；重发仍被截断，就让用户按 README 在 config.toml 补 `model_context_window`、`tool_output_token_limit` 与 `ORTG_AGENT`。这句只发给 codex：别的宿主不认这个指令，发过去只是白占上下文。它同时接在 codex 下 `ortg_overview` 的工具说明末尾（`toolDescription`）：建表的那个会话开始时仓库还没有 ortg.tsv，hook 不注入规则块，模型只能从工具说明里看到它。

**CBM 调用图（可选）**：本机 PATH 里有 `codebase-memory-mcp` 时启用，`ORTG_CBM=off` 关闭。ORTG 用项目名 `ortg-<根路径CRC32>` 自建一份图谱。session 事件在后台脱离进程跑 `ortg graph`（hook 自己立即返回）：先同步 `daemon start` 拉起永久常驻进程（幂等），再 `index_repository --mode fast`——顺序不可反，先建图的话建图命令自带的临时常驻进程会吞掉 `daemon start`、建完就退，之后每次查询都冷启动而超时；这也让重启机器或容器后常驻进程在下一个会话自动回来。`ortg_update` 成功后在 MCP 进程内再刷一次图（同根串行，排队中的多次合并为一次）。pre 注入时用一条 Cypher 查该文件跨文件的 CALLS 边（双向、4 秒超时：常驻时 4 核服务器约 2 秒，且须给宿主 5 秒 hook 时限留出余量），只列表内有纲要、非墓碑、非排除/观察档的文件，每行 `→调用|←被调 路径  文件名[标签]: F:功能`，最多 20 个——完整纲要行已在整份纲要里，不重复。它只是改动的审查范围参考，不写进纲要 R，也不参与对账；CBM 缺失、未建图、超时或出错一律静默不附。只有 CBM 可用时才拉起 `ortg graph`：go test 下可执行文件是测试二进制，拉起它等于重跑整套测试；测试进程由 TestMain 设 `ORTG_CBM=off`。

只有 session 事件写表（对账）；其余只读、不取锁。pre/post 对命中内置排除或忽略规则的路径（ortg.tsv、overview.txt、build/ 等）一律静默。

## 目录纲要

目录纲要就是表里的一行普通纲要，只是写给目录：path 是目录（如 `vendored`），纲要行的文件名以 `/` 结尾（`vendored/[标签]: ...`，CheckEntry 比对文件名时去掉这个 `/`）。它的 B 标签填用到它的模块——内容再独立也不单开模块，并入使用方模块（写进了规则块的"目录纲要规则"）。于是模块清单计数、按 module 取、增量发送、变动重发都与普通条目相同，没有另一套渲染。

- 目录下的文件照常按三档处理，通常放 observe_dirs；ortg_update 对目录纲要不查观察/排除档（那是其下文件的档），只要求目录存在且"以 / 结尾"与路径是否为目录一致，不一致即拒绝。
- 指纹：fingerprintFile 对目录返回零指纹，目录纲要行永不过期；对账枚举只列文件，目录行走"表里有、枚举不到、盘上还在"的分支按存在处理，目录删了才成墓碑。
- 渲染：renderOpts 的过滤对目录纲要行放行（不因其路径落在观察档而被滤掉），它出现在父目录的段里。
- pre 事件：观察档/排除档的文件本来静默；落在某个目录纲要之下时，注入离它最近的目录纲要行，同会话同文件一次（标记 key `folder:<路径>`）。

## 模块列

`ortg.tsv` 的 `module` 列是纲要行标签里的模块，即标签的第三个值（`logic.go[9 G LG L]` → `LG`；标签写成 `[重要度 层级 模块 特征… 规模]`，重要度数字在前，其余以空格分隔的大写字母，模块可两个），落盘时从 outline 算出，不单独维护也不会和纲要漂移；没有纲要的行为空。模块不额外列表：它就在每条纲要行的标签里，纲要头的 `#B模块:` 字典又已列出所有模块名，再在文末按模块重列一遍文件路径等于把整份路径复制一份（实测占整份文档 24%），所以不出这一块；要只看一个模块用 `ortg_overview` 的 module 参数。缺 `module` 列的旧表（十列）由 `migrate.Table` 补一列空 module，下次存盘从 outline 算出。

## 纲要行纪律与纲要头模板

纲要行 `文件名[标签]: Role:职责 | Uses:依赖 | API:对外契约 | Constraints:约束`，标签 `[C A B D… E]` 是重要度数字在前、其后以空格分隔的层级、模块、特征（0 到多个）、规模，每个值一个大写字母（模块可两个）。字段怎么写（纪律随改动后提醒一起发给模型）：

- Role 一句话写这个文件的职责；测试与文档文件只写一句测什么、讲什么，不逐项罗列用例或章节——要改它们时本来就要读文件。
- 测试契约的配额与守护测试清单：Constraints 里含「必须保持」的子句（按 `；`/`;` 切）另计配额 `contractQuota` = 该档配额的一半、至少 100 字，其余约束仍按 `sQuota`；超了各自警告。理由：低重要度文件配额只有 100 字时，为腾地方写测试契约，会话会删掉"非 ASCII 字节会 panic"这类有用约束。守护测试清单由程序从「必须保持」子句的括号里提取（含 `::` 或 `test` 字样的标识符，`GuardTests`），`ortg_review` 对计划文件与全文列出的契约、改后提示对改动文件与它的契约键，各列出至多 40 个具体测试名（`reviewGuardTests`/`impactGuardTests`），要求逐个运行、失败先回到需求，需求里给了命令与期望输出的验收例也要实跑并逐字比对。理由：模型手动跑出了明显错误的输出却没认出来，核对清单只说"运行守护测试"太空泛。
- 测试也调用的入口与执行点：纲要 API 里测试代码要调用的入口写"测试也调用"，不写"单测入口"（提交时出现"单测入口"给警告 `testOnlyWording`）；这类入口照样是对外契约，不得为消除未使用警告加 `cfg(test)`/条件编译或收窄可见性。改后提示附 `apiGuardNote`（文档与清单、配置、数据类文件——json/yaml/toml/lock/xml/ini/cfg/csv——不查）：读改后的文件，纲要 API 列出的名字（≥4 字符的标识符）找不到了就提醒默认保留（需求点名删除或改名才删，删就同步调用方与纲要）；Rust 文件里这些名字的函数落在 `#[cfg(test)]` 下就提醒（各至多 5 个）。理由：为消除未使用警告，模型会给只被测试调用的入口加 `#[cfg(test)]`，本地 cargo test 能过，但换上另一套测试代码（删掉全部 cfg(test) 项）后测试编译失败；纲要把它写成"单测入口"会助长这种做法。同一个参数或限额能由多层执行时，在接线文件纲要或【契约】正文写明唯一执行点；`ortg_target` 对声明了 Keys 的文件传 `=` 时附 `sameWithKeysNote`，提醒改了参数流向或执行点就写完整目标纲要并同步契约；核对清单第 8 项查测试入口可见性、第 9 项查执行点。理由：命令行层把同一个限额同时交给底层与输出层执行，输出层在某种模式下提前停止，而接线文件的目标纲要写的是 `=`，双重执行在纲要里看不见。
- 被测试引用的名字默认保留（`removedTestedNote`）：取文件在 git HEAD 与现在的顶层名字（Python 的 def/class/顶层赋值/import 绑定，现在任意缩进下仍有定义或绑定的——挪进顶层 if/try 的版本分支——算保留，模块级 `__getattr__` 函数体里带引号点名的算保留，import 列表里的注释先去掉；Go 的 func/type/var/const，不含方法；Rust 顶格的 fn/struct/enum/trait/type/const/static/mod，不含 impl 里的方法；Go 与 Rust 同目录别的非测试文件仍定义的算保留；JS/TS 的具名 export，默认导出不算——它在导入处可以取任何名字），对删掉的名字按"定义先于导入绑定、公开先于私有"排序取至多 40 个，用一次 `git grep -w` 找引用（超出的个数在提示里说明），只认测试文件（`isTestPath`）且同语言：Python 须 `from 该模块 import`（含括号多行、相对导入、src 布局后缀），或经绑定到该模块的名字（`import a.b.c as X`、`from a.b import c`）写 `X.名字`，或写出完整点路径；Go 须同目录 `_test.go`，JS/TS 的相对导入须解析到该文件（别名路径按文件名），Rust 须在同一 crate。列出名字与测试文件（`testRefNote`），劝默认保留为不再调用的辅助函数或弃用别名，需求点名才删、删就同改测试。改后提示（Edit 改的文件、Bash 扫到的过期文件与命令点名删掉的文件，至多 5 个）按文件版本（删掉的文件按"已删"）只查一次、按名字组每会话只说一次；`ortg_update` 回复每次附。理由：模型会删掉验收测试仍导入的内部名字（如弃用的辅助函数、旧的常量），整个测试文件收集失败，几十条既有测试记为缺失；本地测试文件已被同步改掉，跑不出来。
- 本地验证盲区：测试配置按依赖版本或平台整类跳过、本地跑不到的测试，在被测文件的 Constraints 里写成「本地验证盲区：X（跳过条件）」（纪律 `updateDiscipline`），改动碰到它们锁定的行为时逐行核对实现；`gateVerify` 与核对清单第 10 项要求按依赖库版本整类跳过的临时去掉门控跑一遍（改动前就失败、只差第三方库输出表示的按实际输出更新期望，`gateTestEdit` 同样把这种漂移排除在行为裁决之外），按平台、网络、可选依赖跳过的不硬跑、记成盲区。理由：依赖新版本库的一批测试在本地环境整类跳过，验收环境却会跑。
- 需求与守护测试冲突的裁决（不让任何一方按规则必胜，免得挡住"需求对、旧测试本该改"的改动）：`ortg_review` 只要列出了契约（按键或同名兜底），就附 `reviewConflict`，要求逐条回答三问——需求是否直接讲到这个场景、期望与守护测试一致还是相反、相反时按证据裁决——裁决顺序命中即停：a 需求点名该测试或说旧行为错/以前是 X 现改为 Y → 改测试与纲要；b 需求说既有测试权威、行为不变、只是重构或迁移 → 保持测试改实现；c 需求有命令与期望输出的验收例 → 实跑为准；d 都没有 → 先求两全，不能两全按需求实现；结果与理由写进下一次 `ortg_review` 的 rulings（每条给了正文的绑定契约一行 `键：裁决`），收敛时程序把它记进契约正文的【裁决】段，后续改动据此一致；缺一条就不收敛。理由：冲突三问只是列出时模型从不回答，会把与守护测试相反的做法写进契约正文。纲要头模板的测试契约规则行与 `gateTestEdit` 用同一顺序（原先一律"不改测试期望值"）。职责迁移：计划文件的目标纲要声明了现在纲要没有的契约键，即视为该职责迁入这个文件，附 `reviewMigration`（列出原参与者），要求新承担者单独生效时也通过原守护测试（暂时关掉原那一层再测），允许两层都保留，但不许旧层兜底掩盖新实现的差别。理由：需求的一条字面要求与守护测试相反，而同一份需求又写了"既有配置不变""冻结测试是权威"（命中 b）；把限额移进新的一层后靠旧层兜底，本地测不出新层的错误。正例 re35、binary3/4 的需求正面写出了新期望输出并解释原因（命中 a），按此顺序会改测试，不被误伤。
- 跨模块契约：不靠调用关系的约定（同一概念由多层共同实现、协议与消息格式、单位、兼容性、HTTP/WebSocket 路由与消息类型、配置键）不写进 Uses。约定本身在纲要头登记一行 `#【契约】键：正文`（键到第一个全角冒号为止，可含 ASCII 冒号与空格；正文写约定与守护测试，全仓库只此一处），每个参与文件在纲要行末尾加可选的第五段 `| Keys:键(角色),…` 声明它（以最后一个 ` | Keys:` 切出，不计入 Constraints 字数，括号里写角色，括号外按逗号/顿号切）。`ortg_update` 与 `ortg_target`（传 `=` 除外）拒收未登记的键（`keysUnregistered`）；`ortg_header` 回复列出登记了却无人声明的键（`keysOrphan`）。`ortg_review` 对计划里每个文件现在与目标纲要声明的键找出涉及的契约（`keyContracts`），按三级排序：登记正文里含多少个计划新引入的标识符（`newTerms`：目标纲要里新出现、不在括号内——括号按惯例是引用测试名——、≥6 字符、出现在不超过十分之一纲要里的标识符），声明它的改纲要文件数，声明它的计划文件数；给正文、全部声明者与命中的标识符的范围：计划里非枢纽文件（声明的键不超过 `hubKeyMax` 8 个）声明的全部键，加上正文命中计划新引入标识符的键——这些是计划绑定的契约，不论目标纲要写的是不是 `=`，每条都要在 rulings 里裁决；只有枢纽文件声明的键不算绑定。不足 `keyFullMax`（6）条按排序补足（补足的不要求裁决），上限 `keyFullCap`（15），绑定的排在前面；其余只列键名与参与者数（`reviewKeysRest`，正文在上下文里的纲要头中）。理由：解析参数的枢纽文件声明了几十个键，一进计划就带出几乎全部契约，契约段可达数万字，真正相关的那条被淹没；排序后它排第一，核对回复长度约减半。计划把底层文件全写成 `=` 时，相关契约只列了键名，模型没看到正文；改为按非枢纽文件绑定后，同一计划给正文的只有少数几条且包含它，核对回复也短得多。`route:`/`ws:`/`msg:`/`event:`/`topic:`/`cfg:`/`env:` 类的键，其值的最后一个空白分隔词是源码字面量，程序在活行文件里查含该字面量却没声明此键的文件，列为疑似漏声明；同名概念兜底（`relatedContracts`）不再重列已按键列出的登记行。改后影响面提示把同键的其他声明者列为 `(契约:键)` 候选。理由：两两连边要求写的人知道另一端、契约正文要么只在一端要么重复漂移（同一行为在两个文件的纲要里很快就成了两种说法）；按键分组的超边只需各自声明参与，正文一处，新参与者声明即并入；字面量查漏不靠猜、也不依赖调用图。
- Uses 只列本文件依赖的跨文件强依赖（≤5），影响面提示、ortg_review 按它反查依赖方。一律写仓库相对路径：文件写全路径，整个目录或包写目录路径并以 `/` 结尾（如 `lib/storage/`，其下所有文件都算被依赖），可加括注写用到什么（括号里的逗号不切分）；包名、模块名、裸文件名都不行，第三方库与标准库不写。`ortg_update` 与 `ortg_target`（传 `=` 时除外）逐项校验：须是表内活行（含计划新建的行）或磁盘上的目录，否则整行拒绝（`usesNotPath`，列出不合格的项）。理由：Uses 写成包名时反查对不上任何文件，改底层的计划从没列出依赖它的输出层；旧规则只说"写文件名或模块名"，没要求路径。旧表里已有的非路径 Uses 不会自动改写，只在重写该行时被要求改成路径；Dependents 对旧行仍按"表内唯一的裸文件名"兼容匹配。
- API 只列跨包或对外的契约（命令、工具名、给别的包用的导出名，以及测试代码要调用的入口），包内标识符不列。给文件新增的对外接口必须写进 API：`ortg_update` 取文件现在的对外符号（Rust 的 `pub` 项，`pub(crate)` 等不算；Go 的导出名；JS/TS 的 `export`），与 git HEAD 里的版本比，新增而 API 里没写的整行拒绝（`newAPINotListed`）；测试文件、文档、HEAD 里没有的新文件与不认识的语言跳过。`ortg_target` 传 `=` 时附 `sameApiNote`：会新增对外接口就别用 `=`。理由：一次任务里绝大多数目标都写成 `=`，其中一个文件新增了对外的限额接口，纲要里却看不出职责变了。
- Constraints 只写不读代码就会做错的约束、不变量与陷阱，不复述 Role 与 API，代码里一眼可见的实现细节不写；字数按重要度配额（`sQuota`：C9 2000 字、C8 1200 字、C7–4 500 字、C3–1 100 字；C9 是删了就跑不起来的核心文件，策略集中、约束最多，单独放宽）。
- **测试契约**：本文件的单元测试或别处的集成测试锁定的对外行为（输出格式、参数组合的结果、边界值、错误语义）写进 Constraints，写成"必须保持 X（测试名）"并写清期望结果，不写成"可能/现状是 X"；这种约束另有模块依赖时（例如一项功能会在模块间迁移），依赖方的纲要里也写上，跨模块的汇总进纲要头【系统】的不可破坏原则。理由：只描述实现的纲要挡不住"改测试期望值迁就实现"和"把被锁定的行为当作现状随手改掉"这两类回归；把行为写成约束并点名守护测试，改动前后才有据可查。

纲要头模板的「整体规范」段写纲要格式、骨架规则、目标规则与测试契约规则，其后是标签说明、A–E 字典与配额行。骨架规则与目标规则在会话开始注入的规则块里也有，纲要头这份不删：规则块靠 hook 注入，hook 没生效时（Codex 还没信任 hooks、只装了 MCP）模型只能从纲要头读到它们。

## 旧格式迁移（migrate 包）

核心（`base` 与 logic.go 的读写逻辑）只认当前格式：`ortg.tsv` 首行不是 `#ORTG-TSV: 2`、或列头不是当前十一列，就返回 `base.ErrFormat`；纲要行只认 `Role/Uses/API/Constraints` 四个字段，文档里只认 `#目标:`。以前各版写下的东西都由同一二进制里的 `migrate` 包转成当前格式，`base` 从不 import 它，logic.go 只有两处调用：

- `openTable`：写入口（会话开始的 session hook、各 MCP 工具与命令）遇到 `ErrFormat` 调 `migrate.Table`，认得的旧表（版本 1：十列无 module、`future_*` 列或当前列头；纲要与目标纲要里的 F/R/A/S 字段与紧凑标签 `[LST8TJAM]`（改写成 `[8 L ST T J A M]`，没有模块的标签保持原样、由门禁提示重写）；纲要头的"未来"字样、旧格式说明行与 `#S配额`；旧模板的规则、格式与标签行整行换成新行，纲要头的行一行不删）就地重写为当前格式，原字节存 `ortg.tsv.old`（不用 `.bak`，升级后第一次存盘就会覆盖它），再重开。认不出的不动，session hook 给格式提示。只读的 pre/post hook 与门禁直接 `base.Open`，遇旧表静默，等会话开始时升级。
- `openOrBootstrap`：无表建表时调 `migrate.Import`：有 overview.txt 就先挪成备份、经 `migrate.Document` 转换后导入；导入失败或零条目而 v1 分卷俱在时改用分卷合成的文档。

淘汰某种旧格式时只删 `migrate/` 里对应代码与测试，核心不动。
