# ORTG v2 策略规则表

与 `logic.go` 不一致时以代码为准。

## 状态判定（每次对账，逐文件，按顺序取第一个命中）

| 顺序 | 状态 | 条件 | 对账动作 | 报告 |
| --- | --- | --- | --- | --- |
| 1 | 忽略 | 命中内置排除或 JSON 忽略规则 | 既有行直接删除，不进表不渲染 | 计数并计入已清除 |
| 2 | 计划新建 | 磁盘无文件，行从未记录过指纹，有目标纲要 | 不置墓碑 | 列出 |
| 3 | 已删除待确认 | 磁盘无文件，其余情况 | 置 deleted=1 作墓碑；文件回到磁盘即清墓碑 | 列出；deleted 与 target_delete 同为 1 的行由 Purge 清除，本轮清除的不再列出 |
| 4 | 无纲要 | 新文件，或 outline 为空 | 插骨架行并记录指纹 | 列出（纲要里只显示裸文件名） |
| 5 | 过期 | 指纹变化且纲要写入时间不晚于文件修改时间（秒级，同一秒算过期） | 无（等模型更新） | 列出 |
| 6 | 待执行 | 有目标纲要或目标删除 | 无 | 列出 |
| 7 | 对齐 | 其余；指纹变化但纲要更新时静默前移指纹 | Align | 只计数 |

内置排除：`.git/`、`build/`、`ortg.tsv`、`ortg.tsv.*`、`overview*.txt`，超过 4 MB 的文件按忽略处理。

上表的完整路径清单由 `ortg_status` 按需返回。`ortg_overview` 的整份、模块、超预算模块清单与已发短回复中，全库状态报告只列计数及 `ortg_status` 指引，不重复附全局路径清单。纲要正文仍按原预算、模块筛选和已发缓存交付：预算内所有文件名照常返回，超预算改给头与模块清单；任务模式另附下述有界政策候选索引，不改变库存、真实纲要、状态判定或测试范围。

任务模式的 `ortg_overview` 还会从本次对账后的活跃认知库存列出标准贡献/开发政策文档候选：顶层贡献、开发或编码规范文件、`.github/CONTRIBUTING`，以及 `doc(s)` 中相应的指南或 index/README/guide 入口（仅 `.md`、`.rst`、`.txt`）。仅列实际仓库相对路径和“无纲要（未知）/已有纲要（摘要）”，不读取正文，不从 vendor、测试样本或目录纲要包中另找文件，也不重复列 AGENTS/CLAUDE。索引按路径排序，最多 8 条、整段最多 2048 字节 UTF-8；路径用可逆双引号引用，过长条目跳过并计入明确的未列数。候选和已有摘要都不证明行为契约；只按原任务相关性阅读正文、核实依据并维护事实纲要，不扩大任务或要求补齐全库文档。载荷沿用每上下文的提示去重，内容变化、force 或上下文重置可再发；在完整回复预算不足时延后且不计已发送，保持原有正文预算、模块流程与最终收尾句。

通用规则交付：通用规则改走独立 MCP 分页：普通 `ortg_overview` 仍按原预算、模块与已发缓存返回纲要，规则未知时只附短通知，不把长纪律混进正文。显式 `ortg_overview rules=""` 从首段开始，省略 `rules` 才是普通纲要；`null` 不等于空串，规则分页不可与 `module` 或 `init` 混用。默认每段连同标题、收尾和 cursor 最多 4096 字节 UTF-8；Codex 同时明确配置有效上下文窗口和正数 `tool_output_token_limit` 时，复用宿主计量与 token 估算合并正文，完整回复不超过显式回包预算的 95%、原生上限及上下文窗口的 50%。未知预算保持保守分页，已知更小预算仍约束完整回复。同一页链固定正文页宽，兼容旧链的 3072 字节；提高预算不改变续页，降低预算后超限的重放或续页拒绝且不推进，可强制重开，逐段确认完整且没有截断提示后，单独回传返回的 `rules` cursor；末段后的下一次回传才确认完成。缺文、旧 cursor 或内容/上下文变化时，以 `rules="" force=true` 重新取送，不并行取页。完整页集包含宿主规则块、纲要纪律及多入口契约；完成记录只表示原生 MCP 按序输出并收到完成 cursor，不证明 SDK 完整消费、语义理解或任务通过。

分页进度及完成记录使用独立 `rules-*` 标记，协议为 `rules-mcp-v1` 并绑定全文指纹、仓库、上下文与本次页链。旧空标记、旧 40 字节指纹及 `Sent.Rules` 均不算新版完成；升级自动要求取页，无需手工 reset。Claude 优先用本上下文自己的转录统一新旧会话 ID，子代理使用自己的转录；标识无法衔接时重新开始，不合并半条页链。resume 保留有效进度，startup、clear、自身 compact 或规则变化使旧链无效；其他会话及父子上下文互不影响。规则取送与 hook 的规则提示逻辑不改写 `Sent` 的 Header、Rows、Solo、Planned、Reviews、未知字段或独立的 Before/Pending/Final 证据。规则未确认时，原门禁覆盖的写入在消耗已有许可前被拒绝；最终审查仍可读取当前代际，只拒绝提交声明。ORTG 自己的工具及规则获取继续通过入口门禁，避免补送死锁。

若宿主未触发会话开始钩子，已注册的 UserPromptSubmit 在收到提示时会检查当前规则确认；规则未知且本上下文尚未输出过对应取页通知时，补发同样的有界 MCP 取页指引。通知按仓库、上下文、规则内容和重置代际去重，正常会话开始已发通知时不重复，连续提示也不刷屏。该记录只表示生成了通知，不确认规则页已消费；不改已发纲要、计划许可或独立实写证据，原写入门禁仍要求分页完成。

改前计划复审另按当前维护模式的核对清单和复审指导正文记录内容指纹，独立于二进制版本。指导变化或旧缓存没有指纹时，重新发送该计划的清单及契约复审指导，并重新建立收敛依据；已取文件纲要及其交付记录、未变规则的分页确认和已保存的契约裁决保留。指导未变继续差量；逐文件提交纲要后，已收敛计划中剩余的原目标仍可继续写入。

会话和子代理启动输出对 JSON 转义后的总量另留信封余量；过长的异常/路径说明退回短通知及 MCP 指引。编辑 hook 也只引用页集或提示补送，不再内联长纪律。

任务实写后还有独立的 final 审查阶段。默认 `ortg_review` 仍核对改前计划；`ortg_review final=true` 读取本调用上下文的当前 `generation`、跟踪路径及有界运行回执。提交时优先用 `requirements` 对象数组逐项写公开要求：`requirement` 是条件，`status` 只能是 `supported`、`failed`、`blocked` 或 `unverified`，`assertion` 写最终实际消费入口、真实断言及结果或阻断/未验证依据，`evidence` 是从本次 final 查询复制的运行 ID 数组。`supported` 必须有当前完整运行引用，且该运行明确退出 0、没有已识别的 pytest 失败或收集错误；没有可靠结果就保留 `blocked` 或 `unverified`。原生工具只核证受信宿主记录存在及当前性，不理解断言，也不自动列全公开要求；命令退出 0、接口摘要和通过计数都不证明语义正确或任务全部验收。只核对任务明确条件，不扩为所有组合、全库测试或未规定的错误文案。数组为 1 至 32 项，JSON 合计至多 4096 字节 UTF-8；放不下时明确其余未验证，不截断后声称全覆盖。旧 `report` 字符串数组保持兼容，同样有 4096 字节上限，与 `requirements` 互斥；提交及 Status 都明确它只是运行依据未核证的自由文本声明，旧声明不会被升级认证。

运行回执复用现有实写状态锁及可信 pre/post hook：按实际 SID（子代理优先）、宿主操作 ID 和 turn 配对，并核对完整命令、工作目录、开始/完成的已跟踪源码代际及 final 代际。缺身份或 pre、输入不符、源码或别的失败代际在运行期间改变、缺退出状态、已知中断/后台/图像结果、宿主或本地输出截断均不能形成可引用回执。新识别 pytest 失败的代际更新与该运行回执同事务写入，因此失败可用 `failed` 引用自己的完整结果，而更早的运行保持陈旧。回执列 SID、操作 ID、目录、命令、源码代际、final 代际、退出码、失败标志、时间及去色输出的长度/摘要哈希；只保留至多 512 字节的完整 pytest 终端摘要，不持久化完整 stdout。每个上下文只保留最近 16 条回执，final 查询的附加回执段最多 4KiB、至多 8 条完整 JSON 记录，另列未展示和陈旧数量；过长记录跳过，不截断身份或猜填已淘汰 ID。读取和声明都不会执行命令，声明也不清除既有 pytest 失败账本。新鲜性只涉及本上下文已跟踪源码，不自动覆盖未归属依赖、环境或整个仓库；信任前提是宿主 hook 载荷及本地状态未被伪造或改写。

只有在 pre 时属于 task 的配对操作实际改变了已识别语言源码内容，才建立该上下文的 final 义务；模式资格固定在 pre，随后切换模式不能改变该操作归属。初读补纲要、无内容变化、manifest/通用配置及纯 metadata 编辑不建立义务，仍保留原库存、角色和日常维护。创建/删除用实际内容或 missing 指纹跟踪；Update、Align、计划 Review 和测试启动不清除义务。新源码 image 或新识别的 pytest 失败使旧声明失效；有宿主操作身份时重复失败 post 去重，没有身份时无法区分重放和同输出新运行，会明确提示并保守失效，不把它当新增测试执行证据。原 pytest 识别、清账及提醒身份保持不变，final 声明也不清失败记录。

final 状态沿现有实写状态锁原子持久化，按实际 AgentID（优先）或 SessionID 分开，跨进程恢复及压缩保留；只允许当前 MCP 调用身份提交本代际。Stop 和 final Review 只复核已经归属的路径；其它上下文改动同一跟踪路径会使旧代际失效；已配对观察到的相交源码变化会同时推进既有上下文的源码代际，即使期间改回原内容或另一操作不在 task 模式，也不能重用旧回执。不新增其他上下文的归属路径或义务，不扫描全库推断未归属的写入。子代理义务不自动移交父会话，父子不能互相结案；未知/未配对写入、未识别文件类型及旧版本未留本阶段证据的历史写入不自动补造义务。内容指纹未知时拒绝声明，状态读写失败明确提示，不伪报完成。

Stop 对未声明代际提供一次有界检查机会：最多 8 个完整可逆引用路径、整段最多 4KiB UTF-8，长路径跳过并明确未列数，未展示路径仍参与代际核对。在原有 12KiB Stop 预算内先容纳该段，余量继续用于原失败记录；放不下则延后且不标已展示。展示标记与声明标记分开，stop_hook_active 时静默且不自动结案；同一代际的检查请求跨恢复不重复，新代际可再提示。它只证明请求被拼入生成的 block/reason 回复，不能保证宿主消费、模型执行或最终语义正确。带宿主身份的 ortg_status 另列当前 final 代际及声明状态；待声明时附与 final Review、Stop 相同的核查指导，不占用 Stop 的展示机会，已声明或无义务时保持简洁，模式切换不隐藏已有义务。纲要对齐不表示 final 已声明，CLI status 无调用身份时不冒认其他上下文。

目标纲要是什么：这个文件改完之后应有的纲要，用来指导接下来改代码——代码改到符合它、用 `ortg_update` 提交后自动清空。待核查、待实测的结论和疑问不是目标，不写进目标纲要，也不写进当前纲要：先核查，再把事实写进当前纲要。它原名"未来纲要"（标记 `#未来:`、工具 `ortg_future`），因为"未来"只说"以后"、被当成了待办事项的去处，改名为目标纲要（`#目标:`、`ortg_target`）；旧标记 `#未来:` 由 `migrate.Document` 在导入 overview.txt 时换掉；`ortg_target` 的 document 只认 `#目标:`。`ortg.tsv` 的列名随之改为 `target_outline`、`target_time`、`target_delete`（模型会去读这个文件），Go 代码里的 Future 名字也都改成了 Target。改名前写的表（列名 `future_*`、纲要头里写着"未来规则""未来纲要""#未来:""ortg_future"）由 `migrate.Table` 就地升级，见下文"旧格式迁移"。

任务纲要生成：普通任务先显式用 ortg_header mode=task。先读原任务和可见测试，列出相关仓库相对路径及关联理由，再逐份读正文，仅生成或修订任务和测试有关文件的纲要。沿合法公共对象的构造或获取、目标调用、输出及实际依赖，将必要 helper 和消费者动态纳入。已有有据且对齐的纲要复用，不为凑全库覆盖补无关文件；未相关裸行保持未知，不宣称全库 ready。可见测试缺失时，依据公开接口和可见调用方形成候选并标未验证，不凭未提供的答案或不可见实现推范围。相关名单只限定纲要生成，不替代用户任务和项目约定的源码、角色或验收范围；保留原库存与已有真实纲要，不通过改忽略/观察角色隐藏无关文件。只有用户明确要求全库初始化才用 mode=build。

持久化维护模式：`ortg_header mode=build` 保留全库初始化顺序，文档未齐时拒绝源码纲要，即使已有源码条目；`mode=task` 解除全部文档前置并按任务范围核查本地提交，仍要求真实纲要头、合法字段和路径以及原目标复审。未覆盖文件不改角色、不补假行，状态仍报告无纲要。不传模式保留配置，空串恢复旧 `hasSourceOutline` 兼容行为。CLI 对应 `ortg header --mode build|task`。任务模式不发送全库阶段完成提示，也不声明语义初始化完成。

任务验收先沿公开合法构造或获取 → 实际调用 → 输出，验证必要 helper 与消费者闭环，再按仓库配置运行完整受影响包及仓库明确规定的验收命令，保留该范围的收集配置，不用函数过滤代替完整包验收。仓库明确要求全仓命令时仍须执行；未规定时，不把无关全仓扫描或测试设为通用前置。相关纲要名单不替代用户任务与项目约定的验收范围，守护测试和已观察失败仍保留证据；未执行或环境阻断明确记为未验证。失败须区分本次回归、任务阻断、既有无关失败及环境或兼容问题，修复范围依任务和项目契约确定，保留失败记录不自动扩大任务。计划核对、task 提交、final Review 和待声明 Status 共用 `taskValidationRule`；它不证明模型实际执行或语义正确。最终持久源码、诊断替代移除、当前配置重建产物与必要验证等候纪律保留。

## Codex 的本地 MCP 审批

Codex 0.159.3 的[官方配置 schema](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/config.schema.json)支持服务器级 `default_tools_approval_mode`。仅在信任本地 ORTG 时，将以下审批项合并到对应的现有配置表；完整接入示例见 README。

手动 stdio 服务器的配置位置：

```toml
[mcp_servers.ortg]
default_tools_approval_mode = "approve"
```

插件提供的服务器使用插件安装标识与服务器名，不把审批项加到插件清单中：

```toml
[plugins."ortg@ortg".mcp_servers.ortg]
default_tools_approval_mode = "approve"
```

本仓库根的 `.mcp.json` 可由 Codex 插件默认发现；插件审批表只覆盖策略，不定义或注册新服务器。只为实际启用的 ORTG 实例补缺项，保留已有服务器、逐工具审批及其他明确权限策略，不重复注册服务器，不改其他 MCP、全局 `approval_policy = "never"`、已有命名 `offline` 权限配置或 shell 网络限制。`model_context_window`、`tool_output_token_limit` 等顶层字段必须放在任何 TOML 表之前。

信任 hooks 不等于批准 MCP 工具；默认审批在 `never` 的非交互调用中可能先于工具执行被拒绝。`approve` 仅跳过该服务器工具的普通审批，逐工具设置仍优先，也不绕过独立的宿主检查，见该版本的[工具调用实现](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/src/mcp_tool_call.rs#L2476)。ORTG 不自动修改用户配置。

需求明确覆盖多个注册、插件或表示实现时，依据可见注册表、文档及调用方列出任务所需且受支持的集合，将各实现的合法调用和适用的转换往返验证逐项对照该集合；子集通过不代表全集，未执行项保留未验证，不扩为无关插件或全库测试。

单项 `path` + `outline` 与批量 `items` 允许路径和纲要文件名内部包含空格、中英文括号；完整批量项按重复文件名与 `[标签]: Role:` 识别边界，目标 `=` / `删除` 从末尾识别，旧格式保持。Uses 分项保留字面括号，仅在完整项不对应表内路径（含计划新建）或磁盘真实路径时逐段剥尾部括注；中间括号不删除，括号内逗号不分项。合法性检查与依赖反查共用同一解析，Keys 的角色语义保持。

`ortg_update` 的 `items` 每项先给路径，再给完整当前纲要行；不能传目标接口的 `=` 或 `删除` 简写。路径仍可为绝对路径，规范化后指向同一文件或目录的重复项拒绝；即使同时给了可用的 path/outline，空数组或 `null` 也不会回退旧接口。批量只合并已经阅读正文及相关测试、完成语义理解的当前纲要，不代替阅读、阶段间修订或改完一个文件立即提交纲要的纪律，不能为了凑批次延迟提交。

批次开始时一次打开并读取表，全部条目在同一个 `Index.Batch` 中校验与写入；任一项校验或逐项写入失败，表、备份、指纹和目标字段不变。最终落盘 I/O 失败时整批未提交，当前表及目标字段不落半批，但 `.bak` 可能已更新为批前完整表，`AtomicWrite` 失败可能遗留临时文件；表替换与备份并非同一个原子存储事务。两类失败都保持会话缓存不变，不清单文件改动记录、不刷新调用图。成功后每项前移指纹并清空目标纲要，表最多保存一次，备份是整批开始前的完整表；成功提交的路径一起从 sentCache.solo 移除，再保存一次缓存并触发一次 CBM 刷新。不会把新条目预记为已发送（之后 overview 仍补发已变动的条目），也不清除 planned 中已经核对收敛的写入许可。目录纲要可与文件纲要同批提交，仍要求目录存在、行文件名以 `/` 结尾，并沿用目录不受其下文件三档配置限制的规则。

当前纲要的依赖（Uses，`-` 算没有依赖）与原纲要不同时，回复仍附提醒检查纲要头描述依赖与分层的部分（如【依赖层次】），不准就用 `ortg_header` 改；纲要头不会自动跟着 Uses 变。头还是模板时不提醒；首次提交条目时，仅在整批完成后没有其他文件缺纲要时提醒，避免初始化逐项刷屏。文档齐门禁以批次开始状态为准：尚无认知档源码纲要且文档未齐时，不能同批补齐文档并首次提交源码，须先提交文档并完成修订。

阶段完成提示在全批成功后按最终状态只生成一次：本批首次补齐全部认知档文件时，优先给最终修订与收尾提炼提示；否则首次补齐全部文档时给文档修订与核心代码阶段提示。重写已有条目不重复触发，失败批次不发成功或阶段完成提示。批量接口继续要求文档 → 修订 → 核心 → 修订 → 普通 → 最终修订；核心选择与语义修订依然由模型依据真实正文执行。

仓库根（`FindRepoRoot`：有 ortg.tsv 的目录，否则 git 根）或 git 顶层有 `ortg.disable` 时永不启用 ORTG（`Disabled`），有表也一样：`ortg mcp` 照常握手，initialize 结果的 `instructions` 只有 `disabledReply` 一句，tools/list 为空（只留隐藏的 ortg_gate，一律放行），模型看不到任何 ortg 工具说明；`HookReplyFull` 对所有事件返回空（Stop 由 main 照常补 `{}`，Codex 要求）；`Gate` 一律放行；`openTable` 报 `errDisabled`，所以 CLI 与 MCP 的读写入口都拒绝、不建表不改表；会话中途才放的文件，已连上的 MCP 对 ortg_overview（含 `init=true`）、ortg_status 回 `disabledReply`。不让 MCP 直接退出的理由（实测）：Claude Code 把启动失败的 MCP 记进全局缓存 `~/.claude/mcp-needs-auth-cache.json`（键 `plugin:ortg:ortg`），此后 15 分钟内任何仓库的新会话都跳过连接 ortg；退出本身不会被反复重启（会话开始 Claude 连试两次、Codex 一次）。

无表即未启用 ORTG：MCP 的 ortg_overview 不带 `init=true`、ortg_status 只回 `noTableReply`（未启用，不要再调用），不建表、不写任何文件；其余 MCP 工具报同一句（`errNoTable`，不再要求模型去建表）。理由：工具说明原写"开工先调用"，模型在任何仓库都会调 ortg_overview，旧实现随手建出 ortg.tsv，连只读的 ortg_status 也建表。只有用户明确要求创建（初始化）或对齐纲要时，模型以 `ortg_overview init=true` 建表，用户自己跑 `ortg scan` 也建表：根目录有 overview.txt 则整份导入为目标纲要，否则用模板建空表；随后把 `ortg.tsv.*` 写入 `.git/info/exclude`。

**首次建纲要：核心文档与入口 → 初始头 → 文档补齐 → 修订 → 核心代码 → 修订 → 普通文件 → 最终修订**：初始头允许根据已读的 README、架构等核心文档与源码入口建立，不要求所有文档已有纲要。初始头建立后，先补齐全部文档纲要，根据完整文档理解修订头和受影响的已有条目；再优先建立入口、基础模块、关键执行链等核心代码纲要，依据代码与相关测试再次修订；最后建立普通文件纲要，通读全库并作最后一轮修订。每轮均检查职责、接口、约束和关系，头用 `ortg_header`，受影响文件用 `ortg_update`，不只改头（`stagedInitRule`）。未覆盖文件继续保留认知档骨架，不会自动忽略或转观察档；初始头或条目对齐不证明语义完成。头仍含模板【部署】/【系统】占位时，源码纲要与计划继续被拒绝，文档纲要可先写；初始头建立后，尚无任何认知档源码纲要时，`ortg_update` 在全部认知档文档补齐前拒绝源码纲要，沿用待建文档提示且不改变表内条目、角色或源码。已有认知档源码纲要的成熟仓库不受此门禁影响，新增文档后仍可更新源码或提交新源码纲要。观察档、排除或忽略行、已删除或不存在的行以及目录纲要不算已有源码认知（`hasSourceOutline`）。文档 Constraints 按 1200 字配额。`ortg_overview` 列出的待建文档 README 优先、最多 20 个，其余记总数；无文档跳过文档阶段。已有初始头后首次补齐最后一个文档，`ortg_update` 提示修订头与已有条目、再进入核心代码阶段（`initDocsCompleteNote`）；首次补齐最后一个认知档文件，提示最终核对头与所有需更新的纲要（`initCompleteNote`）。重写已有条目不会重复触发阶段完成提示；核心代码的选择与阶段间语义修订由模型按已读事实执行，程序不把初始头或格式对齐当作已完成这些核查。**收尾提炼**：纲要头写好后，补上表里最后一个缺纲要的文件（首次提交、提交后没有别的非观察档文件缺纲要）且还有文档在认知档时，`ortg_update` 回复附一句收尾提示（`distillNote`，列出这些文档）：把文档放进观察档（`observe_files`/`observe_dirs`），纲要里不再重复；放之前逐份逐条核对文档纲要 Constraints 里每条约定、约束与设计决定现在写在纲要头哪一段或哪个源码纲要里，找不到落点的先补上（纲要头用 `ortg_header`，源码纲要用 `ortg_update`），文档与代码的不一致也落到对应源码纲要——文档进了观察档，它的纲要就不再发给模型，没落下的内容会丢。程序判断不了覆盖与否，只能靠这句要求；文档以后改了，对账报「观察变动」时重读它、同步纲要头与源码纲要再 `ortg_align`。要留在纲要里的文档（如顶层 README）可以不放。测试同理：观察档里的测试（含整个测试目录）只记指纹、不发给模型，收尾时逐个确认它们锁定的对外行为已按测试契约写进被测源码纲要或纲要头。建源码纲要时就要一并读它的单元测试与相关集成测试（建表指引写明）。这只是提示，程序不强制；重写已有纲要不触发。文档只作背景，与代码不一致时按代码写，并在那份文档的纲要 Constraints 里记下不一致之处。理由：初始全局认知依据已读的核心文档与入口；全部文档纲要不是建立初始头的前置条件；初始头后按上述阶段补齐与修订。未覆盖文件仍是骨架，头写好不等于全库语义初始化完成。

扫描枚举以 git 为准并逐仓库进行：根仓库跑一次 `git ls-files`，再用文件系统遍历找出嵌套的子仓库（发现后继续下钻，多层也能浮出来）各自跑一次，路径加前缀后合并去重。发现子仓库不能问父仓库的 git——git 从不下钻嵌套工作树，根仓库的忽略规则也不管辖它的子仓库（根 `.gitignore` 常有 `/*/` 把所有一级目录藏起来，正是这条遍历要治的盲区）。但**嵌套**仓库的忽略规则算数：一个仓库若落在上层仓库忽略的目录里（vendor/、node_modules/ 之类），连同子树一起跳过——那个项目已经声明了那不是自己的代码。只有目录规则参与剪枝；文件级 pattern 不剪，否则"新被忽略的文件要掉行"依赖的先列出再判 ignored 再 Purge 链路会断。

文件分三档角色，判定顺序 内置结构性排除 > `keep_files` > `observe_dirs`/`observe_files` > `ignore_dirs`/`ignore_files`：**认知**档要写纲要；**观察**档记指纹、报变动但从不要求纲要，也不渲染进整份纲要（`ortg_update` 对它直接拒绝，并指出走 `keep_files`）；**排除**档完全不看。观察档指纹变了报"观察变动"，`ortg_align` 前移指纹即确认——它不是门禁，不阻断任何操作。对账报告里观察档只计数（`观察 N`），只有变动的列出路径。hook 对观察档一律静默。

`ignore_dirs`/`ignore_files` 之外还有 `keep_files`：命中它的路径不再被 JSON 忽略规则排除（压不过调用方内置的结构性排除，ortg.tsv、overview*.txt、build/ 永远在表外）。带 keep 的目录即使命中忽略也照样参与遍历与枚举——先剪掉就再也捞不回来了（取反项不算"这里有白名单目标"，不会让被忽略的目录重新参与遍历）。

**每份名单内部照抄 gitignore**：从左到右扫、后匹配者胜、`!` 前缀取反；同一档内先扫目录名单再扫文件名单，于是具体的文件规则能在宽的目录规则上挖洞（`ignore_dirs: ["vendor"]` + `ignore_files: ["!vendor/keep.go"]`）。整棵留下再挖洞不必拆成几十条：`keep_files: ["composetp/**", "!composetp/vendor/**", "composetp/vendor/critical.yml"]`——留整棵、挖掉 vendor、洞里再把 critical.yml 打回来。**档与档之间的优先级固定，不受名单内顺序影响。**

表里有行、枚举不到、磁盘上却还在的路径：带纲要或目标纲要的按存在处理（被 .gitignore 点名的文件仍有认知，不能当墓碑），只有裸文件名的骨架行判为忽略并由 Purge 清掉——它已经移出扫描范围，留着只是噪音。

建表前先把 overview.txt 重命名为 overview.txt.bak（已存在则 .bak.2、.bak.3，绝不覆盖已有备份）：内容已读进内存，挪开是免得这份旧纲要留在原处，被模型 cat/grep 当成纲要读而绕过 ortg_overview；导入失败时迁移步骤要读的正是这份备份，迁移提示会报出备份名。表不导出任何文本文件——纲要只在 ortg.tsv，只经 ortg_overview 发给模型。建表前已有的 ortg.tsv.bak 原样保留（用户可能正要拿它恢复丢失的表），没有则不留下导入时生成的模板备份；建表后在后台拉起 CBM 建图（`ortg graph`），会话中途建的表也有改动前的调用图可查。

导入 overview.txt 前先经 `migrate.Document` 转成当前格式：剥掉 ORTG v1 的 `#ORTG-CODE-VOLUME:` 卷标记行，把索引换成纲要、v1 字典键 `#A Layer:` 等换成 `#A层级:` 等、行首 `#未来:` 换成 `#目标:`、旧的 F/R/A/S 字段换成 Role/Uses/API/Constraints；导入它与 ortg_target 的 document 时都剥掉渲染加的 `#代码纲要` 标记行（这是当前格式的一部分，留在核心）。导入失败不再删表——空表保留，说明里给出迁移步骤，由模型读旧纲要文档（可能多个）合写成一份合协议的文档，再用 ortg_target 的 document 参数整份提交。每次落盘前先把旧内容写到 `ortg.tsv.bak`，内容未变则不写。唯一例外是 ORTG v1 分卷索引：overview.txt 导入失败而 overview.meta.txt（代码字典）与 overview.code.txt 俱在时，自动换入 v1 字典、整份导入代码卷升级建表（模块卷不迁移），不再要求手工合写；`#S配额` 沿用模板值，因为那才是 logic.go 实际校验的配额。

宿主判定：`ORTG_AGENT` 优先；否则有 `PLUGIN_ROOT` 或 `PLUGIN_DATA` 即 codex。实测 Codex 给 hook 同时导出 `PLUGIN_*` 与兼容用的 `CLAUDE_PLUGIN_*`，Claude Code 只给 `CLAUDE_PLUGIN_*`——所以不能以 `CLAUDE_PLUGIN_ROOT` 为空判 codex，那样会把 Codex 认成 Claude、漏掉下面的预算补充。

宿主差异仍收敛在现有 Host/hook I/O：Codex 的规则页集包含 `codexBudgetRule`，普通大纲要的工具说明继续给出外层 `max_output_tokens`、宿主工具输出预算与分模块取送指引。规则页另用固定小 UTF-8 预算，不依赖放大 hook 限额。模型须核对每页标题、收尾及截断提示再回传 cursor；原生页链和最终 ACK 记录不等于宿主不可截断或模型理解。没有运行付费模型的传输测试只能验收原生输出、回传及状态转换。

**CBM 调用图（可选）**：本机 PATH 里有 `codebase-memory-mcp` 时启用，`ORTG_CBM=off` 关闭。ORTG 用项目名 `ortg-<根路径CRC32>` 自建一份图谱。session 事件在后台脱离进程跑 `ortg graph`（hook 自己立即返回）：先同步 `daemon start` 拉起永久常驻进程（幂等），再 `index_repository --mode fast`——顺序不可反，先建图的话建图命令自带的临时常驻进程会吞掉 `daemon start`、建完就退，之后每次查询都冷启动而超时；这也让重启机器或容器后常驻进程在下一个会话自动回来。`ortg_update` 成功后在 MCP 进程内再刷一次图，items 整批只触发一次（同根串行，排队中的多次合并为一次），失败批次不触发。pre 注入时用一条 Cypher 查该文件跨文件的 CALLS 边（双向、4 秒超时：常驻时 4 核服务器约 2 秒，且须给宿主 5 秒 hook 时限留出余量），只列表内有纲要、非墓碑、非排除/观察档的文件，每行 `→调用|←被调 路径  文件名[标签]: F:功能`，最多 20 个——完整纲要行已在整份纲要里，不重复。它只是改动的审查范围参考，不写进纲要 R，也不参与对账；CBM 缺失、未建图、超时或出错一律静默不附。只有 CBM 可用时才拉起 `ortg graph`：go test 下可执行文件是测试二进制，拉起它等于重跑整套测试；测试进程由 TestMain 设 `ORTG_CBM=off`。

只有 session 事件写表（对账）；其余只读表、不取表锁，配对实写证据另用独立状态锁。pre/post 对命中内置排除或忽略规则的路径（ortg.tsv、overview.txt、build/ 等）一律静默。

## Windows（Codex 的 PowerShell）

hook 命令与 `.mcp.json` 都只调用 `ortg`，Windows 原生解释器按 PATH 找到 `ortg.exe`，无需 `commandWindows`。`tool_input.command` 收字符串；宿主给 argv 数组时按单引号拼成一行再解析，其他形态只当没有命令，不丢弃整份载荷。

shell 解析（`shellSegments`/`shellTargets`/`shellWrites`）在 Windows 上兼容 PowerShell：未加引号的反斜杠后接字母、数字或 `._-` 时保留为路径分隔符（`backslashPaths`，仅 windows 开启）；双引号内反斜杠只转义 `"`、`\`、`$` 与反引号（各平台一致，与 bash 相同）；命令开头单独的 `&` 是调用运算符，只有紧跟 `)` 的 `&` 与命令后的 `&` 仍算后台。命令名经 `shellVerb` 去掉 `.exe` 后缀，`Set-Location`/`chdir`、`Push-Location`、`Pop-Location` 按 cd、pushd、popd 处理；`shellScript` 把 `pwsh`/`powershell` 的 `-Command`（或 `-c`）与 `cmd` 的 `/c`、`/k` 之后的内容当内联脚本递归解析，与 `sh -c` 一致。写入：`Set-Content`/`Add-Content`/`Out-File`/`Tee-Object`/`New-Item`/`ni`/`ac` 取 `-Path`/`-LiteralPath`/`-FilePath` 或第一个位置参数（`-Name` 拼到其后，`-ItemType Directory` 不算写文件）；`Remove-Item`/`ri`/`del`/`erase`/`rd`/`Clear-Content`/`clc` 取全部路径且须已存在；`Copy-Item`/`Move-Item`/`Rename-Item` 及别名按源与 `-Destination`/`-NewName`/第二个位置参数。`-Value` 等其他带值参数不当路径，cmd 的 `/X` 开关丢弃。搜索：`Select-String`/`sls` 的路径参数，或管道前一段是 `Get-ChildItem`/`gci`/`dir`/`ls` 时，及 `findstr`（`/s` 递归）都算代码搜索。

指纹：CRC32 把 CRLF 当 LF 计算，`fingerprint.Raw` 另存原始字节 CRC；表内 CRC 等于其中任一即未变（`fingerprint.matches`），新写入一律存规范化值。因此 `core.autocrlf` 检出与 LF 检出共用一份 `ortg.tsv`，旧表里 CRLF 文件的原始 CRC 也不会整批变成过期。

`AtomicWrite` 在 Windows 上 Rename 失败（读者未开删除共享，hook 读表不取锁）时每 50 毫秒重试，最多约 1 秒，仍失败才按原逻辑报错并留临时文件。`ProcessAlive` 与 `Ancestors` 只读 `/proc`，Windows 上分别为 false 与空：Stop 不做后台整包提醒，`CODEX_HOME` 没有祖先进程回退。

## 目录纲要

目录纲要就是表里的一行普通纲要，只是写给目录：path 是目录（如 `vendored`），纲要行的文件名以 `/` 结尾（`vendored/[标签]: ...`，CheckEntry 比对文件名时去掉这个 `/`）。它的 B 标签填用到它的模块——内容再独立也不单开模块，并入使用方模块（写进了规则块的"目录纲要规则"）。于是模块清单计数、按 module 取、增量发送、变动重发都与普通条目相同，没有另一套渲染。

- 目录下的文件照常按三档处理，通常放 observe_dirs；ortg_update 对目录纲要不查观察/排除档（那是其下文件的档），只要求目录存在且"以 / 结尾"与路径是否为目录一致，不一致即拒绝。
- 指纹：fingerprintFile 对目录返回零指纹，目录纲要行永不过期；对账枚举只列文件，目录行走"表里有、枚举不到、盘上还在"的分支按存在处理，目录删了才成墓碑。
- 渲染：renderOpts 的过滤对目录纲要行放行（不因其路径落在观察档而被滤掉），它出现在父目录的段里。
- pre 事件：观察档/排除档的文件本来静默；落在某个目录纲要之下时，注入离它最近的目录纲要行，同会话同文件一次（标记 key `folder:<路径>`）。

## 模块列

`ortg.tsv` 的 `module` 列是纲要行标签里的模块，即标签的第三个值（`logic.go[9 G LG L]` → `LG`；标签写成 `[重要度 层级 模块 特征… 规模]`，重要度数字在前，其余以空格分隔的大写字母，模块可两个），落盘时从 outline 算出，不单独维护也不会和纲要漂移；没有纲要的行为空。模块不额外列表：它就在每条纲要行的标签里，纲要头的 `#B模块:` 字典又已列出所有模块名，再在文末按模块重列一遍文件路径等于把整份路径复制一份（实测占整份文档 24%），所以不出这一块；要只看一个模块用 `ortg_overview` 的 module 参数。缺 `module` 列的旧表（十列）由 `migrate.Table` 补一列空 module，下次存盘从 outline 算出。

## 纲要行纪律与纲要头模板

纲要行 `文件名[标签]: Role:职责 | Uses:依赖 | API:对外契约 | Constraints:约束`，标签 `[C A B D… E]` 是重要度数字在前、其后以空格分隔的层级、模块、特征（0 到多个）、规模，每个值一个大写字母（模块可两个）。字段怎么写（完整纪律经独立 MCP 页集发送，hook 只短提示）：

- Role 一句话写这个文件的职责；测试与文档文件只写一句测什么、讲什么，不逐项罗列用例或章节——要改它们时本来就要读文件。
- 语义初始化（`semanticInitRule`）：随会话规则、首次建表指引和提交纪律给出。逐个阅读源码正文与可见的相关测试，长文件分段读完；AST、导入和符号清单只辅助定位，不能替代语义概括。Uses 按职责与契约的重要性选择强依赖，不按导入顺序取前五项；API/Constraints 不伪填，也不把未提供的固定文案猜成已知约束。文档或可见测试规定的契约与当前源码实现须分清；已确认的占位、缺失定义或名称绑定缺口及其实际消费者须如实写明，未核实的实现状态不得描述为已实现。当前程序检查覆盖、格式、引用和状态，不能据此证明实际阅读或语义质量。纲要与需求、源码、测试或运行结果冲突时允许核查并修正（`outlineConflictRule`），不是把状态对齐当作正确性证明。
- 任务依赖与最终源码验证（`dependencyBlockerRule`、`finalSourceRule`）：会话规则、核对清单、单文件放行或编辑后影响提示要求：发现缺失符号、导入或依赖缺口时，沿公开合法构造或获取→目标调用→输出的最短必要链，结合可见测试判断是否阻断任务；有依据的阻断纳入计划，不能仅因未点名或早已缺失就排除。“不要求完整子系统”不等于“禁止必要 helper”；显式禁止须遵守，不凭假想外围流程扩展恢复范围，确与任务无关的按证据说明。恢复或迁移缺失符号后，全库搜索实际使用点（含函数对象传递/注册，不能只搜调用括号），逐个消费者核对导入、名称绑定与调用契约；不能只补定义或一个分支，遗漏消费者也纳入计划验证。为绕过仓库缺失实现而临时注入或替换的函数、对象只作诊断；收尾与提交提醒要求去掉这些替代，在新进程中按最终持久源码运行验收。它们是模型执行规则，没有新增自动测试成功或无临时替代的完成凭证。
- 多入口契约（`entryContractRule`）：完整 MCP 纪律要求按入口和触发条件检查 setter、预检、包装及快捷分支；提前校验或迁移后，已规定的异常类型、词句与输出格式仍须满足各入口约定。只验证底层函数不能替代各入口的验证，不从不可见测试猜测未提供的文案。本次改动涉及公开兼容、弃用、异常或告警契约且细节未明时，先读任务相关项目政策与可见消费者，区分强制规定、适用示例及相邻惯例并记录依据和适用边界；不凭习惯猜类型或文案，不将示例升为强制规定。公开包装器或适配层与内部回调的签名、参数可省略性和默认值须分别按可见文档、真实调用方及相关测试核对，不直接照抄内部必填签名；未核实的实现假设不得写成已确认契约或「必须保持」。工厂或装饰器返回可调用对象时，将其公开签名契约与工厂/包装器自身分别核对并记录，依公开任务核对位置参数槽、变参、仅关键字参数、默认值和可省略性；展示用 接口元数据或调用预检 不得相对公开契约额外收窄合法调用，内容/输出选项不隐含改变签名。用公开实际调用形状验收现有调用方及省略可选参数的路径，显式空值不能替代省略验证；未执行的调用形状保留未验证。公开接口对同一参数规定多种值形态或重载时，在 API/Constraints 和目标计划中保留适用上下文、判别依据、整体/逐项语义及返回形态，不能仅凭容器类型一律拆分。对本次改动涉及的适用形态经真实构造与调用，断言公开规定的返回结果或异常；未验证形态保持未知。只打印诊断且命令退出 0 不算语义验收，公开反例须转为实际断言后复验；不扩为无关形态、全组合或全库测试。按任务实际使用的后端与通信入口运行验收；涉及 HTTP、SQLite 等不同实现时分别检查，另一后端或分支通过不能替代任务实际入口的验证。
- 值来源契约（`entryContractRule`）：公开契约明确值来源、对象字段或语义单位时，在 API/Constraints 和目标计划中保留这些约定；沿公开合法构造或获取→实际调用实参→输出/消费的最短传值路径，逐个核对相关调用点的值来源及转换，区分原始值与变换后值。本次改动涉及值表示时，在 API/Constraints 和目标计划中保留来源、允许转换与公开契约决定的比较标准（如语义等价或原始字节/文本一致）；公开契约要求底层、原始或线格式表示时，不能默认以解码后再编码替代，即使业务值相等。缺失与存在但内容为 null、空字符串、0 或 false 是否等价须按已有公开契约核对，未核实等价前不以真值判断合并；自测沿已有合法公开构造或获取链使用真实类型，按该比较标准断言契约独立确定的期望，不以待验证的同一转换链生成期望，替身通过不代替真实入口验证。函数名、类型或调用边存在不证明传值符合契约；用实际调用方路径断言契约结果，不能只测 helper。未核实的来源或契约保持未知，不从参数名或不可见信息猜填，不扩为无关调用点或全库审计。本次改动涉及跨文件或后端传值时，按可见依据核对实参与载荷两侧的单位、表示（如 dtype/端序）、允许范围及相关元数据，将转换映射记入 API/Constraints 或共享契约，并以实际生产值断言消费者结果；名称或语言类型相同不证明表示相同。本次改动涉及影响输出或跨层分支的控制选项时，用能区分公开行为的合法载荷经实际入口断言最终结果；空或默认载荷使分支等价时，不算验证选项效果。
- 分层依赖行为（`entryContractRule`）：调用路径经过适配器或中间层时，将相关默认重试、缓存及异常转换的行为和信号归属纳入 API/Constraints 和目标计划；沿公开生产者→适配/中间层→实际调用方→可观察消费者的任务相关路径，依据可见配置、依赖实现或测试核对实际生效的默认行为，确认状态、返回值或异常由哪层处理、转换或消耗，以及公开契约要求的队列、回调或日志等消费者能观察到什么。类型与调用边一致不能替代层间行为核验；经实际入口断言消费者按公开契约可观察的结果，不能只验证底层结果。未核实的默认行为或信号归属保持未知，不凭依赖名称猜测，不扩为无关层或全库审计。
- 附带失败边界（`entryContractRule`）：公开契约涉及可选、尽力或非致命的附带步骤时，明确主操作结果、附带失败及恢复边界；经本次涉及的全部公共入口验证，已明确可恢复的附带失败不改变已成功主操作的约定结果，并保留取消、退出等控制流语义；未核实的边界保持未知，不将可选直接等同于失败可忽略。
- 测试契约的配额与守护测试清单：Constraints 里含「必须保持」的子句（按 `；`/`;` 切）另计配额 `contractQuota` = 该档配额的一半、至少 100 字，其余约束仍按 `sQuota`；超了各自警告。理由：低重要度文件配额只有 100 字时，为腾地方写测试契约，会话会删掉"非 ASCII 字节会 panic"这类有用约束。守护测试清单由程序从「必须保持」子句的括号里提取（含 `::` 或 `test` 字样的标识符，`GuardTests`），`ortg_review` 对计划文件与全文列出的契约、改后提示对改动文件与它的契约键，各列出至多 40 个具体测试名（`reviewGuardTests`/`impactGuardTests`），要求逐个运行、失败先回到需求，需求里给了命令与期望输出的验收例也要实跑并逐字比对。理由：模型手动跑出了明显错误的输出却没认出来，核对清单只说"运行守护测试"太空泛。
- 公共入口、测试辅助代码与各层职责：纲要 API 按真实外部消费者和项目测试结构记录公共契约；仅被测试调用不自动使一个名字成为公共 API。出现“单测入口”时，`testOnlyWording` 提醒核对实际用途；真正仅用于测试的 helper 可按项目约定使用 `cfg(test)` 等测试配置，公共入口则不能仅为消除警告而收窄签名或可见性。改后提示 `apiGuardNote` 跳过文档、目录及清单配置等数据文件，检查纲要 API 列出的名字（≥4 字符）是否消失，以及 Rust 函数是否落在 `#[cfg(test)]` 下，各至多 5 个；这些只是核查候选，须结合真实调用方和兼容契约决定是否保留或迁移。相同参数或限额经过多层时，在接线文件纲要或共享契约记录各层职责、转换及重复执行约束，是否由单层承担依公开契约决定。`ortg_target` 对声明 Keys 的文件传 `=` 时仍附 `sameWithKeysNote`，参数流向或职责变化须写完整目标纲要并同步契约；核对清单第 8 项检查入口用途，第 9 项检查各层相互作用。
- 被测试引用的名字核查（`removedTestedNote`）：取文件在 git HEAD 与现在的顶层名字（Python 的 def/class/顶层赋值/import 绑定，现在任意缩进下仍有定义或绑定的——挪进顶层 if/try 的版本分支——算保留，模块级 `__getattr__` 函数体里带引号点名的算保留，import 列表里的注释先去掉；Go 的 func/type/var/const，不含方法；Rust 顶格的 fn/struct/enum/trait/type/const/static/mod，不含 impl 里的方法；Go 与 Rust 同目录别的非测试文件仍定义的算保留；JS/TS 的具名 export，默认导出不算——它在导入处可以取任何名字），对删掉的名字按"定义先于导入绑定、公开先于私有"排序取至多 40 个，用一次 `git grep -w` 找引用（超出的个数在提示里说明），只认测试文件（`isTestPath`）且同语言：Python 须 `from 该模块 import`（含括号多行、相对导入、src 布局后缀），或经绑定到该模块的名字（`import a.b.c as X`、`from a.b import c`）写 `X.名字`，或写出完整点路径；Go 须同目录 `_test.go`，JS/TS 的相对导入须解析到该文件（别名路径按文件名），Rust 须在同一 crate。列出名字与测试文件（`testRefNote`），要求核对真实公共兼容契约与测试用途，按任务决定保留入口或同步迁移消费者；测试引用本身不证明该名字是公共 API。改后提示（Edit 改的文件、Bash 扫到的过期文件与命令点名删掉的文件，至多 5 个）按文件版本（删掉的文件按"已删"）只查一次、按名字组每会话只说一次；`ortg_update` 回复每次附。删除仍被引用的名字可能导致收集或编译失败，因此需要核对消费者，而不能只改定义。
- 本地验证盲区：测试因依赖版本、平台、网络或可选依赖而在本地跳过时，在相关源码 Constraints 记录跳过条件和未验证范围，不能把跳过当通过。`gateVerify` 与核对清单要求先核对项目支持环境和适用原因；本次任务涉及相应行为且项目允许时，才在隔离副本或正常改动计划中诊断，临时改动完成后恢复。诊断不能凭本机输出改写断言或选择，不默认永久取消门控；测试修改须有需求或项目公开契约依据。无法执行的保留盲区并说明；失败按本次回归、任务阻断、既有无关失败及环境或兼容问题归因，留账不扩张任务。
- 需求与守护测试冲突的裁决（不让任何一方按规则必胜，免得挡住"需求对、旧测试本该改"的改动）：`ortg_review` 只要列出了契约（按键或同名兜底），就附 `reviewConflict`，要求逐条回答三问——需求是否直接讲到这个场景、期望与守护测试一致还是相反、相反时按证据裁决——裁决顺序命中即停：a 需求点名该测试或说旧行为错/以前是 X 现改为 Y → 改测试与纲要；b 需求说既有测试权威、行为不变、只是重构或迁移 → 保持测试改实现；c 需求有命令与期望输出的验收例 → 实跑为准；d 都没有 → 先求两全，不能两全按需求实现；结果与理由写进下一次 `ortg_review` 的 rulings（每条给了正文的绑定契约一行 `键：裁决`），收敛时程序把它记进契约正文的【裁决】段，后续改动据此一致；缺一条就不收敛。理由：冲突三问只是列出时模型从不回答，会把与守护测试相反的做法写进契约正文。纲要头模板的测试契约规则行与 `gateTestEdit` 用同一顺序（原先一律"不改测试期望值"）。职责迁移：计划文件的目标纲要声明了现在纲要没有的契约键，即视为该职责迁入这个文件，附 `reviewMigration`（列出原参与者），要求新承担者单独生效时也通过原守护测试（暂时关掉原那一层再测），允许两层都保留，但不许旧层兜底掩盖新实现的差别。裁决按当前任务的显式要求及项目公开契约给出依据，不从历史案例推断当前需求。
- 跨模块契约：不靠调用关系的约定（同一概念由多层共同实现、协议与消息格式、单位、兼容性、HTTP/WebSocket 路由与消息类型、配置键）不写进 Uses。约定本身在纲要头登记一行 `#【契约】键：正文`（键到第一个全角冒号为止，可含 ASCII 冒号与空格；正文写约定与守护测试，全仓库只此一处），每个参与文件在纲要行末尾加可选的第五段 `| Keys:键(角色),…` 声明它（以最后一个 ` | Keys:` 切出，不计入 Constraints 字数，括号里写角色，括号外按逗号/顿号切）。`ortg_update` 与 `ortg_target`（传 `=` 除外）拒收未登记的键（`keysUnregistered`）；`ortg_header` 回复列出登记了却无人声明的键（`keysOrphan`）。`ortg_review` 对计划里每个文件现在与目标纲要声明的键找出涉及的契约（`keyContracts`），按三级排序：登记正文里含多少个计划新引入的标识符（`newTerms`：目标纲要里新出现、不在括号内——括号按惯例是引用测试名——、≥6 字符、出现在不超过十分之一纲要里的标识符），声明它的改纲要文件数，声明它的计划文件数；给正文、全部声明者与命中的标识符的范围：计划里非枢纽文件（声明的键不超过 `hubKeyMax` 8 个）声明的全部键，加上正文命中计划新引入标识符的键——这些是计划绑定的契约，不论目标纲要写的是不是 `=`，每条都要在 rulings 里裁决；只有枢纽文件声明的键不算绑定。不足 `keyFullMax`（6）条按排序补足（补足的不要求裁决），上限 `keyFullCap`（15），绑定的排在前面；其余只列键名与参与者数（`reviewKeysRest`，正文在上下文里的纲要头中）。理由：解析参数的枢纽文件声明了几十个键，一进计划就带出几乎全部契约，契约段可达数万字，真正相关的那条被淹没；排序后它排第一，核对回复长度约减半。计划把底层文件全写成 `=` 时，相关契约只列了键名，模型没看到正文；改为按非枢纽文件绑定后，同一计划给正文的只有少数几条且包含它，核对回复也短得多。`route:`/`ws:`/`msg:`/`event:`/`topic:`/`cfg:`/`env:` 类的键，其值的最后一个空白分隔词是源码字面量，程序在活行文件里查含该字面量却没声明此键的文件，列为疑似漏声明；同名概念兜底（`relatedContracts`）不再重列已按键列出的登记行。改后影响面提示把同键的其他声明者列为 `(契约:键)` 候选。理由：两两连边要求写的人知道另一端、契约正文要么只在一端要么重复漂移（同一行为在两个文件的纲要里很快就成了两种说法）；按键分组的超边只需各自声明参与，正文一处，新参与者声明即并入；字面量查漏不靠猜、也不依赖调用图。
- Uses 只列本文件依赖的跨文件强依赖（≤5），影响面提示、ortg_review 按它反查依赖方。一律写仓库相对路径：文件写全路径，整个目录或包写目录路径并以 `/` 结尾（如 `lib/storage/`，其下所有文件都算被依赖），可加括注写用到什么（括号里的逗号不切分）；包名、模块名、裸文件名都不行，第三方库与标准库不写。`ortg_update` 与 `ortg_target`（传 `=` 时除外）逐项校验：须是表内活行（含计划新建的行）或磁盘上的目录，否则整行拒绝（`usesNotPath`，列出不合格的项）。理由：Uses 写成包名时反查对不上任何文件，改底层的计划从没列出依赖它的输出层；旧规则只说"写文件名或模块名"，没要求路径。旧表里已有的非路径 Uses 不会自动改写，只在重写该行时被要求改成路径；Dependents 对旧行仍按"表内唯一的裸文件名"兼容匹配。
- API 只列跨包或对外的契约（命令、工具名、给别的包用的导出名及具有真实外部消费者的入口），仅被测试引用不自动构成公开契约，包内标识符和测试专用 helper 不因此列入 API。给文件新增的对外接口必须写进 API：`ortg_update` 取文件现在的对外符号（Rust 的 `pub` 项，`pub(crate)` 等不算；Go 的导出名；JS/TS 的 `export`），与 git HEAD 里的版本比，新增而 API 里没写的整行拒绝（`newAPINotListed`）；测试文件、文档、HEAD 里没有的新文件与不认识的语言跳过。`ortg_target` 传 `=` 时附 `sameApiNote`：会新增对外接口就别用 `=`。理由：一次任务里绝大多数目标都写成 `=`，其中一个文件新增了对外的限额接口，纲要里却看不出职责变了。
- Constraints 只写不读代码就会做错的约束、不变量与陷阱，不复述 Role 与 API，代码里一眼可见的实现细节不写；字数按重要度配额（`sQuota`：C9 2000 字、C8 1200 字、C7–4 500 字、C3–1 100 字；C9 是删了就跑不起来的核心文件，策略集中、约束最多，单独放宽）。
- **测试契约**：本文件的单元测试或别处的集成测试锁定的对外行为（输出格式、参数组合的结果、边界值、错误语义）写进 Constraints，写成"必须保持 X（测试名）"并写清期望结果，不写成"可能/现状是 X"；这种约束另有模块依赖时（例如一项功能会在模块间迁移），依赖方的纲要里也写上，跨模块的汇总进纲要头【系统】的不可破坏原则。理由：只描述实现的纲要挡不住"改测试期望值迁就实现"和"把被锁定的行为当作现状随手改掉"这两类回归；把行为写成约束并点名守护测试，改动前后才有据可查。

纲要头模板的「整体规范」段写纲要格式、骨架规则、目标规则与测试契约规则，其后是标签说明、A–E 字典与配额行。骨架规则与目标规则在会话开始注入的规则块里也有，纲要头这份不删：规则块经 MCP 分页，hook 没生效或尚未取页时（Codex 还没信任 hooks、只装了 MCP）模型只能从纲要头读到它们。

## 旧格式迁移（migrate 包）

核心（`base` 与 logic.go 的读写逻辑）只认当前格式：`ortg.tsv` 首行不是 `#ORTG-TSV: 2`、或列头不是当前十一列，就返回 `base.ErrFormat`；纲要行只认 `Role/Uses/API/Constraints` 四个字段，文档里只认 `#目标:`。以前各版写下的东西都由同一二进制里的 `migrate` 包转成当前格式，`base` 从不 import 它，logic.go 只有两处调用：

- `openTable`：写入口（会话开始的 session hook、各 MCP 工具与命令）遇到 `ErrFormat` 调 `migrate.Table`，认得的旧表（版本 1：十列无 module、`future_*` 列或当前列头；纲要与目标纲要里的 F/R/A/S 字段与紧凑标签 `[LST8TJAM]`（改写成 `[8 L ST T J A M]`，没有模块的标签保持原样、由门禁提示重写）；纲要头的"未来"字样、旧格式说明行与 `#S配额`；旧模板的规则、格式与标签行整行换成新行，纲要头的行一行不删）就地重写为当前格式，原字节存 `ortg.tsv.old`（不用 `.bak`，升级后第一次存盘就会覆盖它），再重开。认不出的不动，session hook 给格式提示。只读的 pre/post hook 与门禁直接 `base.Open`，遇旧表静默，等会话开始时升级。
- `openOrBootstrap`：无表建表时调 `migrate.Import`：有 overview.txt 就先挪成备份、经 `migrate.Document` 转换后导入；导入失败或零条目而 v1 分卷俱在时改用分卷合成的文档。

淘汰某种旧格式时只删 `migrate/` 里对应代码与测试，核心不动。

## 失败验证记录与空字段验收（0.5.35）

- `CheckEntry` 在解析后拒绝空白的 Role、Uses、API、Constraints，并列出具体字段；无内容必须写 `-`。先剥离可选 Keys，Keys 不替代 Constraints。当前纲要和目标纲要共用校验；旧表读取不被这条新提交规则阻断。
- Bash 的 PostToolUse 识别本仓库内 pytest/py.test 调用及完整汇总，保存同会话工作目录、原命令、失败摘要与逐次调用的测试数量。静态单条前台 pytest 命令（含已知包装命令）且输出以完整摘要结束时，只采用最后一条外层摘要；更早的测试捕获摘要不累计成独立调用。旧版单调用记录的多槽测试数量按最大值保留覆盖门槛，不求和或丢掉较大历史范围。串行多个调用任一失败均保留；循环、管道、后台、动态参数或夹杂其他命令的多摘要输出不猜调用边界。默认只有输出末尾完整、同工作目录、同命令、汇总数与调用数一致，每次通过数量不少于原失败运行且无 skipped/xfailed/xpassed 或未知 outcome，才清除记录。
- 明确非零退出（0.5.88）：已识别的本仓 pytest 命令若有可观测的非零退出码，即使只有 passed 摘要或没有摘要，也记录该次失败、保留旧数量门槛及真实失败 IDs，并经现有操作身份去重使已有 task final 声明过期。进程失败不捏造测试名，也不能证明失败只在旧 IDs 内，须原命令完整范围通过；普通非测试命令失败不新增 pytest 记录或 final 失效。失败/错误摘要即使退出码为零仍是失败。未知退出状态沿用原摘要规则。`HookInput.ToolExitCode` 在截断输出前取可选整数 `tool_response.exit_code`，或从字符串及对象 `output` 开头的完整宿主头部取码；对象字段只是兼容，不保证每个宿主提供。支持 `Wall time`/`Exit code`/`Output:`（也可先 Exit code）及可选 `Chunk ID`/`Wall time`/`Process exited with code`/`Final output:`。结构码优先，不扫描 stdout/stderr、嵌套头部或输出正文。
- 共享摘要解析支持完整的无计时 counts 和 `Interrupted: N errors during collection` 行；相邻同 error 数的中断行与计时统计是一个摘要块，警告、deselected 和收集跳过不产生额外调用。收集中断不揭示选中用例数，保存未知范围且不建立节点证据；同一记录后续失败仍保留这个状态和已有普通测试数量门槛，只能由同目录、同原命令的完整 passed 终端摘要覆盖。静态单条 literal pytest、python -m pytest 或简单 shell -c 包装可仅改变 -q/-v（含 --quiet/--verbose）；比较时保留解释器、环境、路径选择及其余参数，未知选项或包装器不作等价证明，进度行不能解除记录。静态单条的收集中断片段后仍有外层进度等非摘要尾部时，保持未知，不新增捕获失败也不清已有账；完整收集失败尾部仍可记录，前面堆栈被截断不抹掉失败；复合命令仍保留任一摘要失败。成功摘要须有完整计时或首尾装饰，截断标记、缺失尾部、引号里的文字均不能作为结案证据。
- 完整节点证据（0.5.42）：仅静态单条前台直接 pytest/py.test 或 literal `python -m pytest` 的 verbose 运行可建立配置签名，保留执行入口和解释器完整词、受支持行为参数，以及实际运行头中的解释器路径、Python/pytest/plugin 版本、rootdir、configfile、plugins 和其他配置报告；testpaths 只表示本次默认选择，不计签名。仅忽略 verbosity/tb/color 等呈现参数和显式文件/node 选择。配置覆盖、过滤、未知选项、`@argsfile`、环境前缀和包装器保守无节点证据。原失败 IDs 取最后外层 short-summary 的 FAILED/ERROR，完整唯一条数和分类必须匹配最后 failed+error(s)，还须与外层 collected 后、首个报告 section 前的实际 verbose FAILED/ERROR IDs 一致，所有实际 outcome 数量须匹配终端摘要。收集文件错误、截断、混合 stdout、嵌套 banner、歧义或超过 256 个失败节点均无证据。后续同会话、目录、签名的 `-v` 运行，其实际逐节点 PASSED 唯一数量必须等于纯 passed 终端摘要且包含此前全部失败 IDs，才可解除相应记录，即使仅选择这些失败节点。参数化 ID 保留括号内空格和分隔符，歧义不猜；捕获输出或中途 section 不作通过证明。同记录新失败集合与已知失败合并；旧无 ID 或后续不完整证据不能升级成部分节点证明。原始非 verbose、缺运行头、输出达到原生 hook 的末 64KiB 限额均保持原命令完整数量路径，不能事后恢复未知证据；已有配置证据的记录遇到配置头缺失或变化也不清除。
- 失败记录使用根目录与会话隔离的临时标记，跨压缩和进程重启保留，不改纲要表。Stop 在本会话有剩余记录且有未提交代码改动时，逐次记录提醒一次：失败回复按 12KiB UTF-8 字节预算扣除后台提醒后列入尽量多的条目，共同的原范围复测说明只出现一次；目录、命令和摘要过长时保留 UTF-8 边界并明确省略、不可当成完整命令执行。只有列入回复的原 commandKey+At 身份才记录提醒标记，放不下的条目保留且不打标；本次未列数量可能含此前已提醒项，不等于尚未提醒数量，也不承诺下次立即续页。完整节点证据仍最多显示 8 个、合计 2048 字节，标总数且省略时要求取齐。仅有完整证据才提示 verbose 全失败节点复测，其余仍提示原命令完整范围；stop_hook_active、其他会话、无会话或无代码改动时静默。解除失败记录不声明整包或全部契约通过，不更新按维护模式保留的提交核查状态。已知失败与后台仍在运行的原检查分别保留。
- 提示要求沿可见堆栈核实任务阻断；需排除的混合失败按首个异常和实际调用路径分组核证，不能用一个外围或环境缺口替整批其他首因免责。保留原失败范围的证据，按任务核对本次回归与阻断，使用最终源码复验；既有无关失败、环境阻断或尚未修好的项目明确报告依据与剩余失败，留账不自动扩大修复范围。分组核证是模型提示，不新增自动语义分类或门禁。检查以用户任务、项目公开契约和可见运行证据为依据，不证明整个任务成功；其他测试运行器及没有收到汇总的异步完成结果仍不在记录范围内。
