# ORTG v2

单文件纲要引擎。每个源码文件一行模型写的纲要（`文件名[标签]: Role:职责 | Uses:依赖 | API:对外契约 | Constraints:约束`，标签如 `[8 L ST T J M]`：重要度数字在前，其后是以空格分隔的层级、模块、特征、规模，取自纲要头字典），全部状态存在仓库根的 `ortg.tsv`，模型通过 MCP 读整份纲要并回写，宿主 hook 在读代码、改代码时注入纲要与提醒。

## 全库初始化与任务维护

全库建设时调用 `ortg_header mode=build`，继续按文档、核心代码、普通文件及阶段复审的顺序推进。有部分纲要、只处理当前任务时调用 `ortg_header mode=task`，可以提交已读源码的纲要，无需先补齐无关文档。也可用 `ortg header --mode task` 或 `ortg header --mode build` 设置。

模式保存于 `ortg.tsv` 配置，不从自然语言猜测。未传 `mode` 保持原值；传空串恢复旧兼容行为。任务维护仍要求有依据的纲要头、合法字段与路径、契约和改动计划复审；未覆盖文件继续显示为无纲要，切换模式不代表全库初始化完成。

任务验收先沿公开合法构造或获取 → 实际调用 → 输出，验证必要 helper 与消费者闭环，再按仓库配置运行完整受影响包及仓库明确规定的验收命令，保留该范围的收集配置，不用函数过滤代替完整包验收。仓库明确要求全仓命令时仍须执行；未规定时，不把无关全仓扫描或测试设为通用前置。相关纲要名单不替代用户任务与项目约定的验收范围，守护测试与已观察失败仍保留证据；未执行或环境阻断明确记为未验证。失败须区分本次回归、任务阻断、既有无关失败及环境或兼容问题，修复范围依任务和项目契约确定，保留失败记录不自动扩大任务。验收使用最终持久源码；临时替代仅作诊断，测试调用的产物须按实际配置从当前源码重建。

`task` 模式的提交门禁只按独立的 `task:HEAD` 提醒一次任务验收核查；再次提交不表示验证通过。它不推断受影响包，不把局部运行记成整包，不自动扫描或确认全仓版本门控，也不清除已有失败记录。计划核对、final Review 与待声明 Status 使用同一范围指导。`build` 和未设置模式保留原整包门禁。被拦命令中的暂存步骤仍须重跑。

## 获取与构建

```bash
git clone https://github.com/dignfei/ortg.git && cd ortg
```

在仓库根目录执行（需要 Go 1.27，`go.mod` 声明；本机 Go 较旧时会自动下载 1.27 工具链，网络不通就先装好 1.27）：

```bash
CGO_ENABLED=0 go build -ldflags "-s -w" -o build/ortg .
go test ./...
ln -sf "$PWD/build/ortg" /usr/local/bin/ortg   # 放进 PATH；之后重新编译不用再链
```

Windows（PowerShell）构建出 `ortg.exe`，放进用户 PATH 后重开终端与 Codex：

```powershell
$env:CGO_ENABLED = "0"; go build -ldflags "-s -w" -o build\ortg.exe .
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path", "User") + ";$PWD\build", "User")
```

测试套件里有用例直接调用 `bash` 与 `python`，在 Linux、macOS 或 WSL 上运行。

## 安装为插件

Claude Code（会话里 `/plugin …` 与命令行 `claude plugin …` 等价）：

```bash
claude plugin marketplace add "$PWD"   # 在 ortg 仓库根目录执行
claude plugin install ortg@ortg
```

装进去的是仓库工作树在那一刻的拷贝（`~/.claude/plugins/cache/ortg/ortg/<版本>/`），不会自动跟着仓库走。`hooks/hooks.json` 或 `.mcp.json` 改了之后要重新拷一次再重启会话；Claude Code 的插件版本就是仓库当前的 git 提交哈希，没有新提交时 `claude plugin update` 只会说"已是最新"而什么都不拷，所以直接卸了重装。重装前先删掉插件缓存：旧版本的缓存目录还在时，实测重装后缓存里仍是旧版的 `hooks.json`（从 0.1.0 直接装 0.3.39，拿到的是 0.1.0 的 hooks），删掉缓存就整份从仓库重拷：

```bash
claude plugin uninstall ortg@ortg && rm -rf ~/.claude/plugins/cache/ortg && claude plugin install ortg@ortg
```

装完核对缓存里的 hooks 与仓库一致（在仓库根执行，输出 `True`）：

```bash
python3 -c "import json,glob;print(all(json.load(open(f))==json.load(open('hooks/hooks.json')) for f in glob.glob('$HOME/.claude/plugins/cache/ortg/ortg/*/hooks/hooks.json')))"
```

（或者先把改动提交——有了新提交就是新版本——再 `claude plugin marketplace update ortg && claude plugin update ortg@ortg`。ORTG 自己的版本号只写在 `.codex-plugin/plugin.json`，二进制构建时读取它，`manifest_test` 校验 Claude 的两份清单不写版本。）

Codex（codex-cli 0.154 实测）：同样把本仓库当插件市场装上，在 ortg 仓库根目录执行

```bash
codex plugin marketplace add "$PWD"
codex plugin add ortg@ortg
```

之后第一次启动 `codex` 会提示 "Hooks need review"，选"Trust all and continue"，否则 hook 不会运行。信任绑定在 hooks 文件的内容上（Codex 用的是 `hooks/codex.json`：命令式 hook 与 Claude 相同，另有一条按 Codex 的 MCP 名 `ortg` 写的纲要闸门）：以后插件更新改了它（比如新增一条 hook），第一次启动还会再问一次，照样选信任。Codex 的改文件工具是 `apply_patch`，一次可改多个文件：hook 会从补丁头里取出每个文件，逐个注入改动前的纲要、改动后催提交；补丁删掉的文件会被要求用 `ortg_target` 标记删除。

手动注册本地 stdio MCP 时，在 `~/.codex/config.toml` 合并以下配置。仅在信任本地 `ortg` 时补上服务器的默认审批设置；顶层两行必须放在任何 `[表]` 之前：

```toml
model_context_window = 1000000
tool_output_token_limit = 500000

[mcp_servers.ortg]
command = "ortg"
args = ["mcp"]
env = { ORTG_AGENT = "codex" }
env_vars = ["CODEX_HOME"]
default_tools_approval_mode = "approve"
```

Codex 0.159.3 会[默认发现插件根的 `.mcp.json`](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core-plugins/src/loader.rs#L1109)。使用已安装的 `ortg@ortg` 所提供的 `ortg` MCP 服务器时，审批覆盖应放在同一配置文件的以下位置；它只覆盖插件服务器的策略，不注册服务器，不要为此重复添加 stdio 实例：

```toml
[plugins."ortg@ortg".mcp_servers.ortg]
default_tools_approval_mode = "approve"
```

已有配置只补缺项，保留已有服务器、逐工具审批及其他明确权限策略，不要整块覆盖。`"approve"` 设置的只是受信任 ORTG 服务器的默认工具审批，不需要改全局 `approval_policy = "never"`、已有命名 `offline` 权限配置或 shell 网络限制。信任 hooks 与批准 MCP 工具是两件事：在 Codex 0.159.3 中，默认 MCP 审批可能使 `never` 模式下的非交互调用在工具执行前失败。两个配置位置由该版本的[官方配置 schema](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/config.schema.json)支持，`approve` 的普通审批行为见[工具调用实现](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/src/mcp_tool_call.rs#L2476)。

Codex 把工具结果存进对话时另有上限，默认约 1.2 万 token（模型的 truncation_policy × 1.2），超出就从中间截掉、只留首尾，`@exec` 的 `max_output_tokens` 抬不过它；不加 `tool_output_token_limit`，稍大的纲要就被截成半份；`model_context_window` 把上下文调到模型允许的最大值（Codex 会截到模型的 max_context_window，gpt-6-astra 是 87.2 万 token），装得下整份纲要。`env` 让 MCP 进程知道自己跑在 Codex 下（Codex 不给 MCP 进程设 `PLUGIN_*` 变量），纲要大小才按 Codex 的 token 计。`tool_output_token_limit` 对所有工具生效，但 `exec_command` 等工具各有自己的单次默认上限，普通输出不会因此变大。

Claude 与 Codex 的会话 hook 只发短规则通知，对账只列各状态计数，不展开文件路径；恢复且有待处置文件时也只附计数。`ortg_overview` 的每种回复也只附全库对账计数，并提示完整路径清单按需用 `ortg_status` 查看，避免全库未知路径绕过正文预算、模块筛选或重复发送。纲要正文仍按原预算、模块与已发缓存规则交付：预算内保留所有文件名，超预算先给头与模块清单。库存、真实纲要、状态判定与测试范围不变。

通用规则改走独立 MCP 分页：普通 `ortg_overview` 仍按原预算、模块与已发缓存返回纲要，规则未知时只附短通知，不把长纪律混进正文。显式 `ortg_overview rules=""` 从首段开始，省略 `rules` 才是普通纲要；`null` 不等于空串，规则分页不可与 `module` 或 `init` 混用。默认每段连同标题、收尾和 cursor 最多 4096 字节 UTF-8；Codex 同时明确配置有效上下文窗口和正数 `tool_output_token_limit` 时，复用宿主计量与 token 估算合并正文，完整回复不超过显式回包预算的 95%、原生上限及上下文窗口的 50%。未知预算保持保守分页，已知更小预算仍约束完整回复。同一页链固定正文页宽，兼容旧链的 3072 字节；提高预算不改变续页，降低预算后超限的重放或续页拒绝且不推进，可强制重开，逐段确认完整且没有截断提示后，单独回传返回的 `rules` cursor；末段后的下一次回传才确认完成。缺文、旧 cursor 或内容/上下文变化时，以 `rules="" force=true` 重新取送，不并行取页。完整页集包含宿主规则块、纲要纪律及多入口契约；完成记录只表示原生 MCP 按序输出并收到完成 cursor，不证明 SDK 完整消费、语义理解或任务通过。

分页进度及完成记录使用独立 `rules-*` 标记，协议为 `rules-mcp-v1` 并绑定全文指纹、仓库、上下文与本次页链。旧空标记、旧 40 字节指纹及 `Sent.Rules` 均不算新版完成；升级自动要求取页，无需手工 reset。Claude 优先用本上下文自己的转录统一新旧会话 ID，子代理使用自己的转录；标识无法衔接时重新开始，不合并半条页链。resume 保留有效进度，startup、clear、自身 compact 或规则变化使旧链无效；其他会话及父子上下文互不影响。规则取送与 hook 的规则提示逻辑不改写 `Sent` 的 Header、Rows、Solo、Planned、Reviews、未知字段或独立的 Before/Pending/Final 证据。规则未确认时，原门禁覆盖的写入在消耗已有许可前被拒绝；最终审查仍可读取当前代际，只拒绝提交声明。ORTG 自己的工具及规则获取继续通过入口门禁，避免补送死锁。

会话和子代理启动输出对 JSON 转义后的总量另留信封余量；过长的异常/路径说明退回短通知及 MCP 指引。编辑 hook 也只引用页集或提示补送，不再内联长纪律。

任务模式下，`ortg_overview` 为本次所取范围中已交付的真实条目、`ortg_status` 为本会话已取得的条目，附上直接 Uses 中暂无或过期纲要的本地依赖线索。每次最多提示 25 个依赖，去重并标明尚未提示的数量；再次取同范围可续取，压缩或清空后可重发。只看一跳，不展开目录，也不把新依赖递归当根。这不要求全库初始化，不阻止合法提交，不改变正式修复或评测范围；准备阶段必须实际调用这些工具消费线索，已有行齐全不等于依赖语义已核验。

自定义 CODEX_HOME 时，env_vars 将实际配置目录转交给 MCP，避免宿主过滤环境后读错默认配置。Linux 上未转交时，ORTG 只沿当前进程祖先链取最近非空 CODEX_HOME；MCP 自身的显式值优先，无 /proc 或找不到时仍回退用户 ~/.codex。模型窗口上限与有效百分比的计算保持不变。

插件接入不自动改用户配置；MCP 按所用宿主与接入方式配置。不要再把 hook 抄进任何 `settings.json`，也不要用 `claude mcp add` 单独注册 ortg：宿主不去重，多一份注册就是每条钩子跑两遍、两套同名工具。仓库里没有 `ortg.tsv` 时插件对该目录零动作。

### Windows 上的 Codex

安装步骤同上，在 PowerShell 里执行 `codex plugin marketplace add "$PWD"` 与 `codex plugin add ortg@ortg`；手动注册 MCP 时配置文件是 `%USERPROFILE%\.codex\config.toml`。hook 命令只有 `ortg hook --event …`，不含 POSIX 语法，Codex 交给 Windows 原生解释器直接运行；`.mcp.json` 的 `ortg` 同样按 PATH 找到 `ortg.exe`，所以不需要 `commandWindows` 覆盖。

Codex 在 Windows 上用 PowerShell 执行命令，ORTG 按 PowerShell 识别读写：

- 写入：`Set-Content`、`Add-Content`、`Out-File`、`Tee-Object`、`New-Item`、`Remove-Item`、`Clear-Content`、`Copy-Item`、`Move-Item`、`Rename-Item` 及其别名（含 cmd 的 `del`、`copy`、`move`、`ren`）与 `>` 重定向都计入写入门禁；路径取 `-Path`/`-LiteralPath`/`-FilePath`/`-Destination` 或位置参数，`-Value` 等内容参数不当成文件，`New-Item -ItemType Directory` 不算写文件。
- 搜索：`Select-String`（含 `Get-ChildItem … | Select-String`）与 `findstr /s` 按代码搜索处理。
- 目录：`Set-Location`、`Push-Location`、`Pop-Location` 与 `cd` 一样跟踪；`pwsh -Command …`、`powershell -Command …`、`cmd /c …` 包着的命令按里面的命令识别。
- 语法：未加引号的 `src\main.go` 里的反斜杠是路径分隔符；双引号里反斜杠只转义 `"`、`\`、`$` 和反引号；命令开头单独的 `&` 是调用运算符，不是后台运行。

纲要指纹按"CRLF 视作 LF"计算：`core.autocrlf` 检出的工作树与 Linux 上写下的 `ortg.tsv` 保持对齐，不会整库显示过期；旧表按原始字节记下的指纹照样认。Windows 不允许替换别的进程正打开的文件，`ortg.tsv` 落盘遇到并发读取时会重试约 1 秒。

已知限制：判断后台整包测试是否还在跑（Stop 提醒）依赖 `/proc`，Windows 上不提醒；自定义 `CODEX_HOME` 只能经 `env_vars` 转交给 MCP，没有 Linux 那样沿祖先进程回退。Windows 支持按 Codex hooks 文档实现，经交叉编译和 Linux 上的单元测试验证，还没有在 Windows 实机上跑过整套流程。

## 初始化一个仓库

普通具体任务先读任务和可见测试，列相关路径及理由，显式设置 `ortg_header mode=task`，只生成/修订相关纲要；已知且对齐的真实纲要复用，未相关裸行保持未知。相关列表不是代码访问或任务/测试范围限制，合法公共入口与实际调用的必要 helper/消费者动态纳入；可见测试缺失时按公开接口和可见调用方形成候选并标未验证，不凭未提供的答案或不可见实现猜测需求和范围。只有明确要求全库初始化时，才选择 `mode=build` 并按下面的全库阶段推进。

任务模式的 `ortg_overview` 还会从本次对账后的活跃认知库存列出标准贡献/开发政策文档候选：顶层贡献、开发或编码规范文件、`.github/CONTRIBUTING`，以及 `doc(s)` 中相应的指南或 index/README/guide 入口（仅 `.md`、`.rst`、`.txt`）。仅列实际仓库相对路径和“无纲要（未知）/已有纲要（摘要）”，不读取正文，不从 vendor、测试样本或目录纲要包中另找文件，也不重复列 AGENTS/CLAUDE。索引按路径排序，最多 8 条、整段最多 2048 字节 UTF-8；路径用可逆双引号引用，过长条目跳过并计入明确的未列数。候选和已有摘要都不证明行为契约；只按原任务相关性阅读正文、核实依据并维护事实纲要，不扩大任务或要求补齐全库文档。载荷沿用每上下文的提示去重，内容变化、force 或上下文重置可再发；在完整回复预算不足时延后且不计已发送，保持原有正文预算、模块流程与最终收尾句。

任务实写后还有独立的 final 审查阶段。默认 `ortg_review` 仍核对改前计划；`ortg_review final=true` 读取本调用上下文的当前源码代际及跟踪路径，再用返回的 `generation` 和非空 `report` 数组提交模型审查声明。报告依据原公开任务、最终持久源码及必要消费者，把明确的允许/禁止条件、特殊值、组合及输出含义，逐项对应到最终实际消费入口的真实断言及结果，或说明未验证的依据。接口摘要、自测通过计数、纲要对齐或命令启动不能代替逐项依据。只核对任务明确的条件，不扩为所有参数组合、全库测试或未规定的错误文案；报告合计至多 4096 字节 UTF-8，放不下时明确已核对范围及其余未验证边界，不截断后声称全覆盖。原生工具只校验身份、代际、格式及持久化，不验证报告语义或证明未知测试通过。

只有在 pre 时属于 task 的配对操作实际改变了已识别语言源码内容，才建立该上下文的 final 义务；模式资格固定在 pre，随后切换模式不能改变该操作归属。初读补纲要、无内容变化、manifest/通用配置及纯 metadata 编辑不建立义务，仍保留原库存、角色和日常维护。创建/删除用实际内容或 missing 指纹跟踪；Update、Align、计划 Review 和测试启动不清除义务。新源码 image 或新识别的 pytest 失败使旧声明失效；有宿主操作身份时重复失败 post 去重，没有身份时无法区分重放和同输出新运行，会明确提示并保守失效，不把它当新增测试执行证据。原 pytest 识别、清账及提醒身份保持不变，final 声明也不清失败记录。

final 状态沿现有实写状态锁原子持久化，按实际 AgentID（优先）或 SessionID 分开，跨进程恢复及压缩保留；只允许当前 MCP 调用身份提交本代际。Stop 和 final Review 只复核已经归属的路径；其它上下文改动同一跟踪路径会使旧代际失效，不扫描全库推断未归属的写入。子代理义务不自动移交父会话，父子不能互相结案；未知/未配对写入、未识别文件类型及旧版本未留本阶段证据的历史写入不自动补造义务。内容指纹未知时拒绝声明，状态读写失败明确提示，不伪报完成。

Stop 对未声明代际提供一次有界检查机会：最多 8 个完整可逆引用路径、整段最多 4KiB UTF-8，长路径跳过并明确未列数，未展示路径仍参与代际核对。在原有 12KiB Stop 预算内先容纳该段，余量继续用于原失败记录；放不下则延后且不标已展示。展示标记与声明标记分开，stop_hook_active 时静默且不自动结案；同一代际的检查请求跨恢复不重复，新代际可再提示。它只证明请求被拼入生成的 block/reason 回复，不能保证宿主消费、模型执行或最终语义正确。带宿主身份的 ortg_status 另列当前 final 代际及声明状态；待声明时附与 final Review、Stop 相同的核查指导，不占用 Stop 的展示机会，已声明或无义务时保持简洁，模式切换不隐藏已有义务。纲要对齐不表示 final 已声明，CLI status 无调用身份时不冒认其他上下文。

没有 `ortg.tsv` 的仓库就是没启用 ORTG：hook 一律静默，模型调用 ortg 工具也只得到一句"未启用、不要再调"，不建表、不写任何文件。对模型明确说"全库初始化 ortg"（或要求创建、对齐纲要），它才会以 `init=true` 调用 `ortg_overview` 建表：根目录有 `overview.txt`（人手写的纲要文档）就整份导入为目标纲要，并把它改名为 `overview.txt.bak`，否则按模板建空表；然后首扫。纲要只存在 `ortg.tsv` 里，不导出文本文件：模型只经 `ortg_overview` 取纲要，人要看整份可在会话里让模型调用它。命令行等价：`ortg scan`。

要在某个仓库里永远不启用 ORTG，在仓库根（有 `ortg.tsv` 的目录，没有就是 git 根）或 git 顶层放一个空文件 `ortg.disable`。之后 ORTG 什么都不做：`ortg mcp` 只握手，模型看不到任何 ortg 工具，只收到一句"本仓库有 ortg.disable，ORTG 已停用"；hook 一律不输出（Codex 的 Stop 只回它要求的 `{}`）；门禁一律放行；`ortg scan` 等命令行与 `init=true` 都拒绝，不建表也不改已有的 `ortg.tsv`。MCP 不直接退出，是因为实测 Claude Code 会把启动失败记进全局缓存（`~/.claude/mcp-needs-auth-cache.json`），之后 15 分钟内所有仓库的新会话都连不上 ortg。删掉这个文件后，从下一个会话起恢复。

按模板新建的表，纲要头的【部署】【系统】还是占位文字。仅在明确全库初始化时按以下顺序推进：**核心文档与源码入口 → 初始纲要头 → 全部文档纲要 → 修订头与受影响纲要 → 核心代码纲要 → 再修订 → 普通文件纲要 → 最终核对并更新**。先读 README、架构等核心文档全文及源码入口，用 `ortg_header` 建有依据的初始头；随后补齐全部文档纲要，根据最新理解更新头和已受影响的纲要。再优先阅读入口、基础模块、关键执行链等核心代码及相关测试并写纲要，重新核对整体架构和已有纲要；最后处理普通文件，再通读全库作最后一轮修订。每阶段检查职责、接口、约束、关系描述是否变化：头用 `ortg_header`、文件纲要用 `ortg_update`，不只改头。文档阶段与全库条目补齐时，ORTG 的提交回复会提示下一轮修订。初始头无需等全部文档已有纲要；尚无任何认知档源码纲要时，首次提交源码纲要必须等全部认知档文档纲要补齐，提前提交会被原生工具拒绝。已有认知档源码纲要的成熟仓库不受此门禁影响，新增文档不会阻断源码更新或新增纲要；观察档、忽略档、已删除或不存在的行及目录纲要不算已有源码认知。未覆盖文件仍保留认知档骨架，不能把头写好或状态对齐当作全库语义初始化完成。头仍是模板时，源码纲要与计划仍被拒绝；文档 Constraints 按 1200 字配额。没有文档的仓库跳过文档阶段。文档只作背景，纲要按代码实际怎么做来写，两者不一致时按代码写并在那份文档的纲要里记下。没有文档的仓库直接读入口文件与目录结构写纲要头。跨模块、不靠调用关系的约定（同一概念由多层共同实现、协议、单位、兼容性、HTTP/WebSocket 路由与消息、配置键）在纲要头登记 `#【契约】键：正文`（正文只写这一处），参与的文件在纲要行末尾加 `| Keys:键(角色)`；改动涉及某个键时，`ortg_review` 列出契约正文与全部参与者，路由、消息、配置类的键还会在源码里查出用了字面量却没声明的文件。需求与守护测试冲突时按证据裁决（需求点名该测试或说旧行为错→改测试；需求说测试权威、行为不变或只是迁移→保持；有验收例→按实跑；都没有→先求两全）：`ortg_review` 给出正文的契约，每条要在下一次核对的 `rulings` 里写一行「契约键：裁决」，缺一条计划就不收敛，收敛时裁决记进该契约正文末尾的【裁决】段；职责从一个文件迁到另一个文件时，新承担者要单独通过原守护测试。按真实外部消费者和项目测试结构区分公共入口与测试辅助代码：公共入口写入 API，不得仅为消除警告而收窄签名或可见性；真正仅用于测试的 helper 可按项目约定使用 `cfg(test)` 等测试配置。改后提示提供候选，仍须依据实际调用方核实。相同参数或限额经过多层时，写明各层职责、转换及重复执行约束，是否由单层承担依公开契约决定。给文件新增对外接口（Rust `pub` 项、Go 导出名、JS/TS `export`）必须写进 API：提交时与 git HEAD 版本比，新增却没写的会被拒，所以会新增接口的文件在计划里不要写 `=`。Uses 一律写仓库相对路径（整个目录或包写目录路径并以 `/` 结尾，如 `lib/storage/`；第三方库不写），提交时逐项校验，写成包名、模块名或裸文件名会被拒——依赖方按路径反查，写不成路径的依赖会被漏掉。写源码纲要时一并读它的单元测试与相关集成测试，按**测试契约**把被测试锁定的对外行为写进 Constraints：写成"必须保持 X（测试名）"并写清期望结果，而不是"现状是 X"；跨模块的汇总进纲要头。所有文件都有纲要后，ORTG 在最后一次 `ortg_update` 的回复里提示收尾：逐条核对文档纲要里的每条约定、以及观察档里测试锁定的行为，已写进纲要头或某个源码纲要（没有的先补上），再把文档放进观察档（`observe_files`/`observe_dirs`），避免同一内容在纲要里写两遍；之后文档改了，对账会报「观察变动」。改代码时，`ortg_review` 的核对清单与改动后的提示都会要求运行纲要里点名的守护测试；测试失败时先核对需求与项目公开契约；测试期望或测试选择的修改须有这些依据，不能仅为让当前实现或本机输出通过而修改。

写源码纲要须阅读源码正文（长文件分段读完）及可见的相关测试。AST、导入和符号清单可辅助定位，不能代替语义概括；Uses 按职责与契约的重要性选择强依赖，不能按导入顺序机械截取前五项。API/Constraints 无内容不伪填，不把未提供的固定文案猜写成已知约束。条目齐全和状态对齐不等于语义质量已核验；遇到需求、源码、测试或实际运行结果冲突时，核查对应源码与测试并修正纲要。

需求明确覆盖多个注册、插件或表示实现时，依据可见注册表、文档及调用方列出任务所需且受支持的集合，将各实现的合法调用和适用的转换往返验证逐项对照该集合；子集通过不代表全集，未执行项保留未验证，不扩为无关插件或全库测试。

`path` + `outline` 与 `items` 均支持路径和纲要文件名内部的空格、中英文括号。批量完整行按重复的文件名及 `[标签]: Role:` 识别路径与纲要的边界，旧空格或制表符分隔格式保持；目标的 `=` 和 `删除` 从末尾识别。Uses 在括号外按逗号或顿号切分，保留路径中间的括号；表内路径（包括计划新建）或磁盘上的真实完整路径优先，否则只逐段剥掉尾部括注（括注内部的逗号不切分）。合法性仍按原有活行或目录规则检查，依赖反查使用同一解析规则；Keys 的角色括注解析保持。

Shell 文件路径按命令当前目录（含可解析的 `cd`）逐个解析，只认精确落在本仓库内的库存路径。缺失的相对文件和外仓库的绝对路径不会借同名文件或路径后缀匹配本仓文件；无法静态确认的包装命令保持未知。

有宿主操作标识且改前、改后载荷能配对时，ORTG 对明确写路径记录实际内容变化；这些认知档文件必须提交新纲要，`ortg_align`（含 CLI）不能替代。尚未收到完成事件的明确写路径若当前内容已不同于改前或最近成功 Update 的记录，Align 只临时拒绝前移，不生成永久待维护记录或推断作者；无变化、操作前已有漂移及已提交后未再变化的内容允许对齐。这也覆盖同一 shell 操作内写文件后立即调用 CLI align 的顺序。记录跨进程、会话与压缩保留，只有成功的 `ortg_update` 确认对应路径，失败不清除；观察档和未观察到实写证据的人工存量对齐保持原行为。

采样仅覆盖文件编辑工具与可解析的前台 shell 明确写文件，不展开目录或扫描库存；缺操作标识、配对不符、读取失败、动态或包装命令保持未知。只比较操作前后的内容，不能排除期间的外部并发写入；已删除路径仍走原删除确认流程。实写记录在固定状态目录加锁，不跨目录回退或自动抢占中断残锁；残锁会有限超时报错，须确认没有持有者后修复确切状态锁。纲要表与实写记录分别落盘：表已提交但记录保存失败时会明确提示并保留旧记录，恢复存储后重提对应纲要。

提交纲要时，Role、Uses、API、Constraints 四个字段都必须有值；没有有依据的内容就写 `-`，空字符串、纯空白或只写 `Keys` 不能替代必填字段。工具会指出具体空字段，修正后再提交。

`ortg_update` 也支持一次提交多个已阅读文件的当前纲要。初始化的文档门禁按整批开始前的状态判定：尚无源码认知且文档未齐时，不能在同一批里补文档并首次提交源码，要先完成文档批、按提示修订，再进入核心代码阶段。批量提交不会代替文档 → 修订 → 核心 → 修订 → 普通 → 最终修订，也不代替源码正文及相关测试的阅读。阶段提示按整批成功后的状态只生成一次；全库补齐时优先提示最终修订，重写已有条目不重复触发。

本会话的 pytest 输出若有失败或错误，ORTG 会保存原命令与失败摘要，跨上下文压缩和进程重启保留。默认仍要求同工作目录、同命令的每次调用完整通过，测试数量逐次未缩小且没有跳过或预期失败。对于静态单条前台的直接 `pytest` 或同一解释器的 `python -m pytest`，如果原失败运行用 `-v` 保留解释器与运行配置头，外层实际逐节点结果与最后的真实 short test summary 一致且完整列出全部失败节点，则可以在同会话、目录和配置下用 `-v` 只复测全部这些节点；只有逐节点实际 `PASSED` 覆盖全部已记录失败、数量与纯 passed 终端摘要一致，才解除记录。参数化节点按完整 ID 匹配，包装器、动态命令、配置覆盖、未知参数、收集错误、混合测试 stdout、嵌套运行头、缺失或截断证据都保守回到原命令完整范围。原生 hook 只保留输出末 64KiB，广测的 verbose 输出达到此限额也不能建立节点证明；旧记录与原始 `-q` 或普通非 verbose 输出不事后补猜证据，因此此路径不能让所有巨大全库运行免于原范围复测。证据最多保存 256 个失败节点，超过时保留原范围要求；Stop 的失败展示部分按 12KiB 的 UTF-8 字节预算列出尽量多的真实失败运行（后台提醒先占预算），共同的完整范围复测说明只列一次；过长字段明确标为非完整命令摘要，溢出说明本次未列数量且保留记录，仅列入回复的原命令与时间身份记为已提醒。节点仍只展示有限数量并标总数。代码仍有未提交改动时，Stop 对每次记录提醒一次：按记录要求验证最终持久源码，沿可见堆栈处理任务阻断；确实无关、环境阻断或尚未修好的，说明证据与剩余失败。解除记录只说明已观察失败被覆盖，不保证整包、全部契约或用户与项目要求的完整验收通过；提交前仍按维护模式与仓库规定命令核查，也不要求无限重试。

可观测的明确非零退出码也会记录为该次 pytest 运行失败，即使摘要全是 passed 或没有摘要；不能清除既有失败记录，并会使 task 模式中已有的 final 审查声明过期。已有真实失败节点与数量门槛保留，但进程失败的范围保持未知，仍须原命令完整范围通过。失败或错误摘要即使退出码为零也保留。退出状态缺失时沿用原摘要规则；普通非测试命令退出失败不进入 pytest 账本。状态只取工具响应对象的可选整数 `exit_code`（兼容字段，并非所有宿主都提供）或文本开头完整的宿主头部：`Wall time`、`Exit code`、`Output:`，或 `Chunk ID`、`Wall time`、`Process exited with code`、`Final output:`；也支持 `Exit code` 在 `Wall time` 前。结构码优先，不扫描 stdout、stderr 或头部后的正文来猜状态。

节点证明还要求运行头位于输出开头、完整摘要位于末尾。工具附加的 stdout 前缀、拼在摘要后的 stderr 或启动 warning，都会让这一证明保持未知；这类输出需要先处理可见原因或按原范围要求验证，不能删日志内容伪造通过证据。

从旧纲要文档迁移：导入时（`migrate` 包）自动把索引换成纲要、英文字典键换成中文键、`#未来:` 换成 `#目标:`，所以只是措辞老旧、格式仍合协议的文档可直接导入。格式也不合的（如旧的数据库表行、多套标签体系），导入会失败但保留空表并给出迁移步骤，由模型把旧文档（可能是多个文件）合写成一份合协议的文档，再用 `ortg_target` 的 `document` 参数整份提交。从 ORTG v1 分卷索引迁移则全自动：`overview.txt` 是 v1 根清单、分卷（overview.meta.txt 代码字典、overview.code.txt 条目）还在时，`ortg scan` 直接升级建表，存在的文件进纲要、缺失的进目标纲要；模块卷不迁移。

## 用法

每次开一个新会话（Claude Code 或 Codex），按这个顺序说：

1. 第一句问：

   ```
   纲要对齐了吗？
   ```

   模型会实时重新对账（调用 `ortg_status` 或 `ortg_overview`，两者都会重扫），报告对齐、过期、无纲要各多少。有未对齐的文件时，程序会同时给出三个处置选项，回数字即可（1 立刻逐个补纲要 / 2 人工已核对只前移指纹 / 3 先不处理）。

2. 第二句说：


3. 然后写你的实际需求，比如新增功能、修复 bug 等。

模型据整份纲要定位要动的文件，只读纲要没写到的具体细节；改完一个文件会顺手提交它的新纲要，让纲要跟着代码保持对齐；改动后还会列出可能受影响的候选文件（全局纲要里 Uses 写到它的、CBM 调用图里调用它的——改动后先同步更新调用图再查，并保留更新前的调用方，改名时要跟着改的文件不会漏），并让模型通读全局纲要找出语义相关的（同一概念、配置、数据格式或约定），逐个判断哪些要跟着改代码、哪些只需重写纲要。会话一开始，hook 只提示模型先调 `ortg_overview`：整份纲要同时过两道线才一次全给：估算的 token 不超过上下文窗口的一半，大小不超过宿主单次截断值减一点余量（Claude 约 48 万字、Codex 约 48 万 token）。token 按实测拟合的公式估：Claude 约 1.08×中文字符 + 0.53×其他字符，Codex 约 0.91×中文字符 + 0.25×其他字符（固定的「字/token」比例在中文多和代码多的纲要上会差三成）。窗口：Claude 取 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`，没设时看模型是否带 `[1m]`（`ANTHROPIC_MODEL`，或会话开始的 hook 记下的模型；只有交互会话的 hook 带模型，`claude -p` 不带）——带就是 100 万、否则 20 万；Codex 读 `~/.codex/config.toml` 的 `model_context_window`（截到模型上限）或 `models_cache.json` 里模型的窗口，再乘 Codex 实际可用的比例，读不到就只看截断值。纲要一直留在上下文里、压缩后还会重发，超过窗口一半就没多少空间干活了；超过时先给纲要头和模块清单，模型再按问题取相关模块。大小按宿主自己的算法计：Claude Code 按 JS 字符串长度（UTF-16 码元，汉字算 1），Codex 按 UTF-8 字节 ÷ 4 估 token。纲要只发一次：同一会话里已发给模型的条目不再重发，再取只补还没有或已变动的；上下文被压缩或清空（`/compact`、`/clear` 等）后自动重发；以 `--resume` 续接同一对话（宿主换了新进程，哪怕它给 MCP 换了新的会话 id——ORTG 按这个对话的转录认会话）时沿用已发记录，不重发——重启机器后续接也一样：已发记录等会话状态存在 `ORTG_STATE_DIR`（缺省用户缓存目录下的 `ortg/`，Linux 即 `~/.cache/ortg`），不放常在重启时清空的 `/tmp`。单次超过上限（Claude 50 万字、Codex 50 万 token，各减一点余量）照发（可能被截断），开头提醒模型按拆分原则（按业务域与职责、沿 Uses 依赖稀疏处切、公共底层单独成模块、每模块宜在单次上限的十分之一以内）拟一份拆分方案给用户，用户同意后改 B 标签并登记 #B 字典。

任务执行发现缺失符号、导入或依赖缺口时，沿公开合法构造或获取→目标调用→输出的最短必要链，结合可见测试判断是否阻断任务；有依据的阻断纳入计划，不能仅因未点名或早已缺失就排除。“不要求完整子系统”不等于“禁止必要 helper”；显式禁止须遵守，不凭假想外围流程扩展恢复范围，确与任务无关的按证据说明。恢复或迁移缺失符号后，全库搜索实际使用点（含函数对象传递/注册，不能只搜调用括号），逐个消费者核对导入、名称绑定与调用契约；不能只补定义或一个分支，遗漏消费者也纳入计划验证。这些是模型核证提示，不自动判定语义或保证执行。为绕过仓库缺失实现而临时注入或替换的函数、对象只算诊断；提交或结束任务前须移除这些替代，在新进程里用最终持久源码运行验收。同一契约由 setter、预检、包装或快捷分支处理时，按入口与触发条件分别验证已规定的异常类型、词句和输出格式，不只测底层函数。本次改动涉及公开兼容、弃用、异常或告警契约且细节未明时，先读任务相关项目政策与可见消费者，区分强制规定、适用示例及相邻惯例并记录依据和适用边界；不凭习惯猜类型或文案，不将示例升为强制规定。公开包装器或适配层与内部回调的签名、参数可省略性和默认值须分别按可见文档、真实调用方及相关测试核对，不直接照抄内部必填签名；未核实的实现假设不得写成已确认契约或「必须保持」。工厂或装饰器返回可调用对象时，将其公开签名契约与工厂/包装器自身分别核对并记录，依公开任务核对位置参数槽、变参、仅关键字参数、默认值和可省略性；展示用 接口元数据或调用预检 不得相对公开契约额外收窄合法调用，内容/输出选项不隐含改变签名。用公开实际调用形状验收现有调用方及省略可选参数的路径，显式空值不能替代省略验证；未执行的调用形状保留未验证。公开接口对同一参数规定多种值形态或重载时，在 API/Constraints 和目标计划中保留适用上下文、判别依据、整体/逐项语义及返回形态，不能仅凭容器类型一律拆分。对本次改动涉及的适用形态经真实构造与调用，断言公开规定的返回结果或异常；未验证形态保持未知。只打印诊断且命令退出 0 不算语义验收，公开反例须转为实际断言后复验；不扩为无关形态、全组合或全库测试。按任务实际使用的后端与通信入口运行验收；涉及 HTTP、SQLite 等不同实现时分别检查，另一后端或分支通过不能替代任务实际入口的验证。

公开契约明确值来源、对象字段或语义单位时，在 API/Constraints 和目标计划中保留这些约定；沿公开合法构造或获取→实际调用实参→输出/消费的最短传值路径，逐个核对相关调用点的值来源及转换，区分原始值与变换后值。本次改动涉及值表示时，在 API/Constraints 和目标计划中保留来源、允许转换与公开契约决定的比较标准（如语义等价或原始字节/文本一致）；公开契约要求底层、原始或线格式表示时，不能默认以解码后再编码替代，即使业务值相等。缺失与存在但内容为 null、空字符串、0 或 false 是否等价须按已有公开契约核对，未核实等价前不以真值判断合并；自测沿已有合法公开构造或获取链使用真实类型，按该比较标准断言契约独立确定的期望，不以待验证的同一转换链生成期望，替身通过不代替真实入口验证。函数名、类型或调用边存在不证明传值符合契约；用实际调用方路径断言契约结果，不能只测 helper。未核实的来源或契约保持未知，不从参数名或不可见信息猜填，不扩为无关调用点或全库审计。本次改动涉及跨文件或后端传值时，按可见依据核对实参与载荷两侧的单位、表示（如 dtype/端序）、允许范围及相关元数据，将转换映射记入 API/Constraints 或共享契约，并以实际生产值断言消费者结果；名称或语言类型相同不证明表示相同。本次改动涉及影响输出或跨层分支的控制选项时，用能区分公开行为的合法载荷经实际入口断言最终结果；空或默认载荷使分支等价时，不算验证选项效果。

调用路径经过适配器或中间层时，将相关默认重试、缓存及异常转换的行为和信号归属纳入 API/Constraints 和目标计划；沿公开生产者→适配/中间层→实际调用方→可观察消费者的任务相关路径，依据可见配置、依赖实现或测试核对实际生效的默认行为，确认状态、返回值或异常由哪层处理、转换或消耗，以及公开契约要求的队列、回调或日志等消费者能观察到什么。类型与调用边一致不能替代层间行为核验；经实际入口断言消费者按公开契约可观察的结果，不能只验证底层结果。未核实的默认行为或信号归属保持未知，不凭依赖名称猜测，不扩为无关层或全库审计。

公开契约涉及可选、尽力或非致命的附带步骤时，明确主操作结果、附带失败及恢复边界；经本次涉及的全部公共入口验证，已明确可恢复的附带失败不改变已成功主操作的约定结果，并保留取消、退出等控制流语义；未核实的边界保持未知，不将可选直接等同于失败可忽略。

会话里还没加载纲要就去读、搜、改代码时（比如上下文压缩之后，或一上来就 grep），第一次会被拦下并提示先调 `ortg_overview`；只拦这一次，之后每个文件附一句提醒；已加载就不打扰，大仓库只在碰到还没取的模块时提醒去取那个模块。这个检查跑在本会话的 ortg MCP 进程里，不另起进程（Claude Code 与 Codex 都有）。纲要发没发过、门禁拦没拦过都按会话记：同一仓库里别的会话或线程压缩、清空上下文，不会让本会话重发整份纲要或再被拦；本会话自己压缩或清空后重发时，开头会写明几点被压缩还是被清空。

只改一个文件时直接改，改完提交它的纲要（第一次写时 ORTG 附一句提醒）。要改多个文件（含新建、删除）时必须先定计划并自查：用 `ortg_target` 的 `items` 一次写全这次要改、新建、删除的每个文件的目标纲要（每项 `路径 目标纲要行`，纲要不变写 `=`，计划删除写 `删除`），调用 `ortg_review` 按全局纲要逐项核对（接口与调用方、数据与约定、测试与文档……；它还会按目标纲要里新出现的标识符，列出计划外纲要里同名概念的「必须保持」条目，要求逐条说明新实现是否仍满足），核对列出要补、要核实的地方时，补改后再核对，连续两次核对计划不变、且给了正文的契约都写了裁决（`rulings`）才解锁这些文件；计划全写 `=`（只改实现），或第一次核对没发现要补的地方（没有不合格的目标纲要、缺目标纲要的依赖方、要裁决的契约、同概念的「必须保持」条目或职责迁移），一次核对即解锁。核对给正文的契约：计划里非枢纽文件（声明的契约键不超过 8 个）声明的全部键，加上正文命中计划新引入标识符的键，至多 15 条；只被枢纽文件（如解析全部参数的文件）声明的键只列名。判定方法：计划外已写、还没提交纲要的文件只能有一个，再写第二个（包括 `sed -i`、`>` 重定向、`rm` 等 shell 写入）就拦下，要求先列计划；前一个文件提交纲要（`ortg_update`）后，下一个文件又算单文件改动。观察档文件（如测试目录）不写纲要，不参与判定。测试配置与其它认知档文件一样遵守写入计划，没有因包含版本跳过条件而豁免的通道。这一步是模型自查，不给用户看、不等同意，核对完直接动手。只改实现、改完纲要不变的文件（重构、格式化、修 lint），目标纲要传 `=` 即可，不必把整行纲要再抄一遍，纲要里只显示一行 `#目标:同现在`。改测试文件时 ORTG 会提醒一次：测试期望和测试选择的修改须有需求或项目公开契约依据，本机观察输出本身不能充当依据。同一计划的后续核对只回差量：目标没变的文件只列名，已给过正文的契约只列键，冲突三问与核对清单每个计划只发一次。`build` 或未设置模式的兼容流程保留原提交前整包检查：自最近一次改代码以来没跑过按仓库自己配置、不加 `-k`、不只跑单个文件或子目录、不覆盖 `addopts` 等收集配置的整包测试，ORTG 会把这次提交拦一次（同一提交点再提交即放行）。被拦的是整条命令，同一条命令里的 `git add` 等暂存也没执行，拦截提示会说明这一点；同一提交点再提交时命令既不暂存、其间也没单独暂存过，就再拦一次，提醒先把要提交的改动暂存上——否则只有此前已暂存的内容进入提交。`build`/兼容模式中，测试配置（conftest.py，限 testpaths 之内）里按依赖版本整类跳过测试的分支，ORTG 会自动检出，随纲要一起列出（在条目之后、对账报告之前）；`build`/兼容模式中，门控尚无诊断运行或核查确认记录时，提交会得到一次提醒，条件是否在本环境成立仍须核实；再次提交只记为已确认提醒，不证明实际运行或测试通过。先依据项目支持环境和跳过原因判断适用范围；需要且项目允许时，在隔离副本或正常改动计划中诊断，临时改动完成后恢复。诊断结果不自动授权永久取消门控或改写断言。测试运行选中的用例全部被跳过时，改后提示会立即提醒"跳过不等于通过"；去掉门控后跑出失败时，逐项区分本次回归、任务阻断、既有无关失败和环境或兼容问题，不推断本机与 CI 的结果必然一致。改了依赖清单里已有依赖的版本（与 git HEAD pytest 失败会按原命令和工作目录保留，完整摘要包括无计时的 counts 和 `Interrupted: N errors during collection` 行。收集中断的 error 数不代表选中的用例数，范围未知且不建立节点覆盖证据；须同目录、同原命令给出完整 passed 终端摘要，已有普通失败的数量门槛仍保留。静态单条的 literal pytest、python -m pytest 或简单 shell -c 包装可仅调整 -q/-v（含 --quiet/--verbose）保留汇总，其余解释器、环境、路径选择和参数须相同；未知选项或包装器不认作等价，双 -q 只有进度行时仍保留记录。成功摘要须有完整计时或首尾装饰，缺失、截断或引号里的摘要不能结案；只有同命令完整通过、各次测试数量未缩小才覆盖。静态单条 pytest 命令只采用输出末尾的完整摘要，测试捕获输出里的嵌套失败摘要不另计；收集中断行后仍有外层进度等非摘要尾部时，单条命令保持未知，不新增捕获失败也不解除已有记录；复合命令保留前一次调用的真实失败，循环、管道、后台、动态命令及缺失或截断摘要仍保守处理。整包测试放到后台或脱离会话启动、还没跑完且改动未提交时，结束回合会被 Stop 回复会列出名字与测试文件；核实真实公共兼容契约与测试用途，按任务决定保留接口或同步迁移消费者，不能仅因被测试引用就推断为公共 API。测试配置按依赖版本或平台整类跳过、本地跑不到的测试，在被测文件纲要里写成「本地验证盲区」。纲要的 Constraints 字数配额按重要度：C9 2000 字、C8 1200 字、C7–4 500 字、C3–1 100 字。

### 批量提交当前纲要

原生 MCP 工具 `ortg_update` 保留 `path` + `outline` 的单文件接口，也接受 `items` 字符串数组，每项为 `路径 完整纲要行`。以下是工具的参数示例，路径和标签须换成当前仓库的实际值：

```json
{
  "items": [
    "src/reader.go reader.go[5 L K T]: Role:读取记录 | Uses:- | API:Read | Constraints:返回读取错误",
    "src/writer.go writer.go[5 L K T]: Role:写入记录 | Uses:- | API:Write | Constraints:返回写入错误"
  ]
}
```

给了 `items` 就只走批量接口，忽略同时传入的 `path` 和 `outline`；空数组、`null`、格式不完整的项、规范化后重复的路径都拒绝。每项须写当前完整纲要，不能用目标纲要的 `=` 或 `删除` 简写。绝对路径仍可用。一批只打开一次表，共用一个 `Index.Batch`，表最多备份和保存一次，不逐项调用完整 `Update`；任一项校验或逐项写入失败，整批回滚，表、备份、指纹和目标字段均保持原状，错误指出失败路径与原因。最终落盘 I/O 失败时整批未提交，当前表及目标字段不会落下半批更新，会话缓存不变、调用图不刷新；但 `.bak` 可能已更新为批前完整表，`AtomicWrite` 失败也可能遗留临时文件。

成功时每项前移指纹并清空目标纲要，随后整批只保存一次移除已提交路径的单文件改动记录，并刷新一次调用图。提交不会把新条目预记为已发送，也不会取消已核对计划的写入许可；后续 `ortg_overview` 仍能补发变动后的条目。存在性、三档角色、目录与行末 `/` 一致性、格式与字典、四字段非空、Uses 路径、Keys 登记和新增 API 校验仍逐项执行，目录纲要可与文件纲要同批提交。批量只合并已经完成正文阅读的当前纲要，适合初始化或一并重写受影响的条目；改完一个文件立即提交新纲要的纪律仍须执行，不能为凑批次延迟提交。

## 三档角色：认知 / 观察 / 排除

每个文件落在三档之一，判定顺序是**内置结构性排除 → keep_files → observe_* → ignore_***：

| 档 | 配置 | 行为 |
| --- | --- | --- |
| 认知 | 默认，或 `keep_files` 捞回 | 要写纲要；没写就一直在"无纲要"里催 |
| **观察** | `observe_dirs` / `observe_files` | 记指纹、报变动，**不要求纲要**、不进渲染出的整份纲要。内容变了报"观察变动"，`ortg_align` 确认即可，不阻断任何事 |
| 排除 | `ignore_dirs` / `ignore_files` | 完全不看，表里的行也清掉 |

测试、fixture、生成的配置放"观察"档：你想知道它们变了，但不想为每个都维护一行纲要。想为观察档文件建立正式认知，把它加进 `keep_files`（keep 压过 observe）。

**怎么改这些配置**（本节与下一节的 JSON 片段都是 `ortg.tsv` 里那个 JSON 对象的键，不是能单独执行的东西）。两种做法：

- 对模型说，例如"把 testdata 放进观察档""忽略 node_modules"，它会调用 `ortg_header` 改好。
- 手工编辑：打开仓库根的 `ortg.tsv`，找到纲要头下面那个 `{ … }` 对象，把片段里的键合并进去（新表是 `{}`，要补上外层大括号，键之间加逗号），保存后执行 `ortg scan` 让它生效。

### 目录纲要：整个文件夹一条

第三方库、vendored 代码这类**不改内容**的目录，不必逐文件写纲要：把目录放进观察档，再给**目录本身**写一行纲要。它就是一个普通条目，只是文件名以 `/` 结尾。在会话里对模型说一句（换掉目录名、描述和模块）：

```
把 vendored 配成目录纲要：第三方库 foo v1.2，只读不改，升级走 go get 后 go mod vendor；它给 K 模块用
```

模型会把 `vendored` 加进 `observe_dirs`，再对路径 `vendored` 提交一行：

```
vendored/[3 L K T]: Role:第三方库 foo v1.2 | Uses:- | API:- | Constraints:只读不改,改行为去上游提 PR,升级走 go get 后 go mod vendor
```

- **并入用到它的模块**：目录纲要的内容往往自成一体，但不单开模块——B 标签填用到它的那个模块（上例是 K）。于是它算进模块清单里 K 的文件数，模型取 K 模块时一起拿到，增量发送、变动重发也和普通条目一样。这条也写进了注入给模型的规则里。
- **推荐观察档而不是排除档**：观察档照样记指纹，有人升级或手改了库，下次对账会报"观察变动"。只有 `node_modules` 这种体积巨大、变了也无所谓的才用 `ignore_dirs`；排除档的目录同样可以写目录纲要。
- 描述写清**是什么、版本、能不能改、怎么升级**，模型据此决定要不要读具体文件。模型真要改目录里的某个文件时，改动前会被注入离它最近的目录纲要，同会话同文件一次。
- 目录纲要行不会过期（目录本身没有内容指纹），目录还在就算对齐；目录删了会变成墓碑，和文件一样。
- `dirs`（`ortg_header` 的参数）只是纲要里目录段的标题，和目录纲要无关。

## 忽略与白名单

`ignore_dirs`/`ignore_files` 是减法，`keep_files` 是加法：整个目录忽略掉、只留里面几个用得到的文件，就写

```json
"ignore_dirs": ["node_modules", "vendor", "composetp"],
"keep_files": ["composetp/docker-compose.yml", "composetp/.env"]
```

`keep_files` 压过 `ignore_dirs` 与 `ignore_files`，但压不过内置的结构性排除（`ortg.tsv`、`overview*.txt`、`build/`）。

**每份名单内部按 gitignore 的规矩来**：从上往下扫，**后匹配者胜**，`!` 前缀取反。所以整棵留下再挖洞不用拆成几十条：

```json
"ignore_dirs": ["composetp"],
"keep_files": ["composetp/**", "!composetp/vendor/**", "composetp/vendor/critical.yml"]
```

整个 composetp 留下 → vendor 那块挖掉（落回 ignore 判定）→ 洞里的 critical.yml 再打回来。同一档内先扫目录名单再扫文件名单，所以 `ignore_files: ["!vendor/keep.go"]` 能在 `ignore_dirs: ["vendor"]` 上打一个洞。**档与档之间的优先级是固定的，不受顺序影响**。带 keep 的目录即使被忽略也照样遍历——否则里面的文件根本不会被列出来，白名单也就无从生效；被忽略的子仓库同理。

## 多仓库工作区

根目录下嵌套独立子仓库时，每个仓库用它自己的 `git ls-files` 枚举，再合并——git 不下钻嵌套工作树，只问根仓库会让子仓库整个消失。根 `.gitignore` 藏起子目录不影响住在里面的仓库；但子仓库自己忽略的目录（vendor/、node_modules/）里的仓库会连子树一起跳过。

## 可选：CBM 调用图

装了 [codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp)（二进制在 PATH 里）就自动启用，不用配置：改文件前的注入会多出一段"调用图关联文件"，列出调用它和被它调用的文件（最多 20 个，只给文件名、标签和 F 字段）。图谱由 ORTG 在会话开始和每次 `ortg_update` 成功后于后台增量刷新，`items` 整批只触发一次，项目名为 `ortg-<8位hex>`。没装、未建图或查询超过 4 秒都静默跳过。设 `ORTG_CBM=off` 关闭。细节见 `docs/rules.md`。

### 新机器安装

1. 只装二进制，不让它改各 agent 的配置（ORTG 只用它的 `cli` 模式；要它自己的 MCP 工具就去掉 `--skip-config`）：

   ```bash
   curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh | bash -s -- --skip-config
   command -v codebase-memory-mcp   # 默认装到 ~/.local/bin，必须在启动 Claude/Codex 的那个 PATH 里
   ```

2. 常驻进程与图谱不用手动配置，由 ORTG 自己管：每次会话开始，session hook 在后台跑 `ortg graph`，先 `codebase-memory-mcp daemon start`（幂等，已在跑就直接返回），再为本仓库增量建图。重启机器、重启容器之后，下一个会话会把常驻进程重新拉起来，不需要 systemd 或 cron。

   常驻进程不能缺：没有它，每次查询都要冷启动（快机器约 2.7 秒，4 核服务器超过 4 秒），会超过 pre hook 的 4 秒查询时限，关联段会静默消失；有它约 1–2 秒。顺序也不能反：先建图的话，建图命令会自带一个临时常驻进程，`daemon start` 撞上它只回"已在运行"，建完图就跟着退了。

   想不开会话就手动预热，在仓库里跑：

   ```bash
   ortg graph                          # 拉起常驻进程并刷新本仓库调用图
   codebase-memory-mcp daemon status   # 应显示 active (permanent)
   ```

3. 验证：在已启用 ORTG 的仓库开一个新会话，然后

   ```bash
   codebase-memory-mcp cli list_projects --limit 1000 2>/dev/null | grep -o "\"name\":\"ortg-[0-9a-f]*\",\"root_path\":\"$PWD\""   # 在该仓库根目录执行，应输出一行 ortg-xxxxxxxx
   ```

   之后让模型 Edit 一个有调用关系的文件，注入里应出现"调用图关联文件"一段。

升级 CBM 用 `codebase-memory-mcp update`：升级会停掉常驻进程，下一个会话开始时自动拉起；升级后要重开 agent 会话。

## ortg.tsv 格式

三段：首行 `#ORTG-TSV: 2`，随后以 `#` 开头的纲要头；一个 JSON 对象（`ignore_dirs`、`ignore_files`、`keep_files`、`observe_dirs`、`observe_files`、`dirs`）；列头加十一列 TSV：`path crc32 ignored deleted mtime module outline outline_time target_outline target_time target_delete`。`module` 是纲要行 B 标签，落盘时从 outline 算出，不单独维护；核心只认这一种格式，列头不符即 `ErrFormat`；旧版写的表（版本 1：十列无 module、`future_*` 列名、纲要行的 F/R/A/S 字段与紧凑标签、纲要头里的"未来"字样）由同一二进制里的 `migrate` 包在会话开始或写入口就地升级，原文件留在 `ortg.tsv.old`；认不出的（多半是比 ortg 新的表）停用本会话并提示升级 ortg。单元格不含制表符与换行，按 path 排序，原子落盘；每次内容变化前先把旧文件存为 `ortg.tsv.bak`（与 `.lock`、`.tmp*` 一起由 `.git/info/exclude` 排除，不进表）。损坏的 `ortg.tsv` 会被拒绝加载而不是覆盖，可从 `.bak` 恢复。旧格式兼容全部在 `migrate/`：核心不 import 它，只有 logic.go 在 `ErrFormat` 时调 `migrate.Table`、建表时调 `migrate.Import`；哪天不要某种旧格式，只删 `migrate/` 里对应代码。与代码不一致时以 `base/tsv.go` 为准。

## 本仓库自用

`ortg.tsv` 的 `ignore_dirs` 需包含 `纲要设计`；`overview.txt` 与 `ortg.tsv` 本身内置排除。

本仓库不自己注册 hook（`manifest_test` 守着）：hook 由装好的插件提供，再抄一份就是跑两遍。根目录 `.mcp.json` 是插件的 MCP 声明，在本仓库里又会被当成项目 MCP 与插件那份重复，所以 `.claude/settings.json` 用 `disabledMcpjsonServers` 把它关掉。

命令（直接执行 `ortg` 看完整用法）：`ortg scan`、`ortg status`、`ortg align --all` 或 `ortg align 路径...`、`ortg target --path P --outline L`、`ortg target --path P --delete`、`ortg target --document FILE`、`ortg graph`、`ortg hook --event E`（宿主调用）、`ortg mcp`（宿主调用）。策略规则表见 `docs/rules.md`。
